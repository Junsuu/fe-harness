# fe-harness

**FE 코드 품질 루프.** 커밋과 푸시 시점에 코드를 검증하고 리뷰한다.
같은 지적이 반복되면 그걸 규칙으로 올린다 —
**루프가 돌수록 지적이 줄어드는 것**이 이 도구의 목표다.

| 시점 | 보는 범위 | 하는 일 |
| --- | --- | --- |
| **커밋할 때** | 이번 변경만 | 검증 · 리뷰 · 개선 · 기록 |
| **푸시할 때** | 브랜치 전체 | 커밋 사이에 생긴 문제 · 반복된 지적의 규칙화 |

**스킬 · 훅 · 서브에이전트를 플러그인 내부에 직접 구현하지 않는다.**
마켓플레이스에서 검증된 것들을 **역할에 맞게 끼워서** 쓰고,
무엇을 끼울지는 설정 한 줄로 바꾼다.

🚧 **개발 중.** 설계와 근거: [docs/DESIGN.md](docs/DESIGN.md)

---

## WHY

Claude Code 로 프로젝트 작업을 진행하면서 아래와 같은 상황을 겪었다.

- 컴포넌트가 점점 비대해진다
- 같은 코드가 여기저기 중복된다
- 한 파일이 여러 역할을 진다
- 가독성이 계속 떨어진다

파일이 길어지는 게 원인인 줄 알고 길이를 막아봤지만 나아지지 않았다.
길이는 증상이지 원인이 아니었다.

**원인은 만들기만 하고 되돌아보지 않는 것이었다.**

```
현재:  설계 → 작성 → 커밋 → 설계 → 작성 → 커밋 …      부채가 쌓인다
목표:  설계 → 작성 → 검증 → 리뷰 → 개선 → 커밋 → 학습  개선이 쌓인다
```

## 루프는 어떻게 도는가

### 한 바퀴 = 커밋 한 번

커밋한 직후에 네 단계를 돈다. 아직 커밋 전이면 커밋 안 한 변경을 본다.

| 단계 | 무엇을 보나 | 누가 판단하나 |
| --- | --- | --- |
| **① verify** | **정답이 있는 것** — 중복이 늘었는가, 타입·린트·테스트가 통과하는가 | 프로그래밍 도구 |
| **② review** | **읽어야 아는 것** — 이 컴포넌트가 두 가지 일을 하는가 | 모델 |
| **③ refine** | 지적을 고칠 수정 코드까지 제시 | 적용 여부는 사람 |
| **④ learn** | `findings.md` 에 한 줄 기록 | — |

그리고 이 결과가 **다음 작업의 컨텍스트가 된다.**

```bash
/lap           # 위 네 단계
```

**커밋하면 자동으로 돈다.** 훅이 백그라운드로 검사를 끝내고 결과를 물려주므로
사람의 작업을 막지 않는다. FE 파일이 안 바뀐 커밋은 건너뛴다.
`/lap` 은 손으로 부르고 싶을 때 쓰는 같은 절차다.

### 그리고 푸시할 때 한 바퀴 더

커밋할 때 도는 내부 루프는 **그 시점의 단일 커밋만** 본다.
그래서 커밋 A 와 커밋 C 사이에 생긴 중복은 잡아내지 못한다.

```bash
/lap push      # 푸시 전 — 브랜치 전체
```

| | `/lap` (내부) | `/lap push` (외부) |
| --- | --- | --- |
| 보는 범위 | 이번 커밋 | 브랜치 전체 |
| 중복·죽은 코드 | **몇 건 늘었는지** | **총 몇 건인지** |
| **승격 제안** | 안 함 | **함** |
| 비용 | ~1분 | 수 분 |

승격 제안은 외부 루프에서만 한다.
**매 커밋마다 물으면 성가시고, 성가시면 끄게 된다.**

### 루프 반복을 통해 개선되는 방법

여기가 이 도구의 전부다.

지적 → `findings.md` 에 카테고리와 함께 기록 → 같은 카테고리 **3회** → 승격 제안

승격은 지적의 성격에 따라 셋 중 하나로 간다.

| 지적의 성격 | 어디로 올리나 |
| --- | --- |
| 기계적으로 판정 가능 | `hookify` 규칙 (block / warn) |
| 판단이 필요한 지침 | `CLAUDE.md` |
| 이 저장소만의 맥락 | `.fe-harness.json` 의 `guidance` |

- **제안만 한다.** 확인 없이 규칙을 추가하지 않는다. 스스로 규칙을 늘리는 도구는 통제가 안 된다.
- **승격한 항목은 카운트에서 뺀다.** 같은 걸 매번 물으면 결국 끄게 된다.
- **승격 뒤 새로 3회 쌓이면 다시 제안한다.** 규칙이 부족했다는 신호다.

### 개선 여부 확인 방법

**커밋당 새로 나오는 지적 수가 줄어드는가.** 이게 유일한 지표다.
늘어난다면 부채가 쌓이는 속도를 루프가 못 따라가는 것이고,
그때는 코드를 쓰는 시점의 개입(`guide`)을 늘려야 한다.

`.fe-harness/findings.md` 는 회고용이 아니라 **계기판**이다.
그래서 커밋하는 것을 권한다. 히스토리가 없으면 추세를 볼 수 없고,
3회 카운트도 세션을 넘겨 쌓여야 한다.

로컬에만 두려면 `.gitignore` 에 `.fe-harness/` 를 추가하면 된다.
다만 그러면 팀이 같은 지적을 각자 3번씩 받는다.

## 역할과 도구

루프의 각 칸을 **역할**로 정의하고, 거기에 어떤 도구를 끼울지는
`.fe-harness.json`이 정한다. **플러그인 코드는 특정 도구 이름을 모른다.**

| 역할 | 하는 일 | 기본값 |
| --- | --- | --- |
| **guide** | 쓰기 **전에** 기준을 컨텍스트에 넣는다 | `frontend-fundamentals` 스킬 |
| **verify** | 객관적으로 틀린 것을 잡는다 | 린터 · tsc · `jscpd` · `knip` |
| **review** | 읽어야 아는 것을 본다 | `frontend-fundamentals:reviewer` |
| **refine** | 지적을 수정 코드로 옮긴다 | 없음 (모델이 직접) |
| **record** | 커밋·PR 문구를 요점만 쓴다 | `commit-commands` |
| **learn** | 반복된 지적을 규칙으로 올린다 | `hookify` |

### 무엇이 어느 칸에 가는가

이 분류가 설계 전체를 결정한다.

```
프로그램이 판정할 수 있다   → verify   타입 · 린트 · 테스트 · 중복 · 죽은 코드
셀 수는 있지만 판단이 필요   → 신호만   파일 길이 · 컴포넌트 개수
읽어야 안다                → review   응집도 · 이름 · 패턴 선택 · 시맨틱
```

**중복과 죽은 코드가 `verify`에 있는 게 핵심이다.** 프로그램이 판정할 수 있고,
**동시에** "틀렸다"고 단정할 수 있다. 이런 건 도구에 맡기는 쪽이 정확하고
비용도 낮다.

**반대로 셀 수 있어도 틀렸다고 단정할 수 없는 것이 있다.**
정당하게 어기는 코드가 실제로 있다.

- 아이콘 래퍼를 모아둔 배럴 파일은 컴포넌트가 스무 개여도 정상이다
- 데이터 테이블 · API 응답 타입 정의 · SVG 컴포넌트는 길어야 정상이다
- 본체와 함께 둔 표현용 래퍼는 같은 파일에 있는 편이 읽기 좋다

개수나 길이만 보고 막으면 이런 코드가 전부 걸린다.

**그래서 차단하는 훅이 하나도 없다.** 세는 것은 신호로만 남기고,
그 개수가 문제인지는 `review`가 읽고 판단한다.

## 설치

**사용할 플러그인의 마켓플레이스를 먼저 등록.** (의존성 미해결 시 플러그인 비활성)

```bash
claude plugin marketplace add toss/frontend-fundamentals
claude plugin marketplace add anthropics/claude-plugins-official

claude plugin marketplace add <이 저장소 경로 또는 URL>
claude plugin install fe-harness@fe-harness

claude plugin list      # Status 확인
```

- 마켓만 등록돼 있으면 의존 플러그인(`frontend-fundamentals` · `hookify` · `commit-commands`)은 **자동 설치**
- **기본 설정에 적힌 도구는 전부 필수.** 하나라도 없으면 그 역할이 조용히 비고, 그건 도는 척하는 것이다
- **`validate --strict` 는 로드 성공을 보장하지 않는다.** 매니페스트가 멀쩡해도 훅이 안 붙을 수 있어 `Status` 를 봐야 한다

## 설정

프로젝트 루트에 `.fe-harness.json` 을 둔다. 없어도 동작한다.

| 상태 | 동작 |
| --- | --- |
| 파일이 있다 | 그대로 쓴다. 추론하지 않는다 |
| 파일이 없다 | 린터 · 포매터를 추론한다 |
| 추론도 실패 | 아무것도 하지 않는다 |

전체 예시는 [`.fe-harness.example.json`](.fe-harness.example.json).

```json
{
  "roles": {
    "guide":  ["frontend-fundamentals:readability", "frontend-fundamentals:cohesion"],
    "review": "frontend-fundamentals:reviewer",
    "refine": "",
    "record": "commit-commands:commit",
    "learn":  "hookify"
  },
  "verify": {
    "lint": "",
    "typecheck": "pnpm typecheck",
    "duplication": "npx jscpd --min-lines 8 --reporters json --silent",
    "deadcode": "npx knip --reporter json"
  },
  "signals": { "maxNewFileLines": 250, "maxEditLines": 80, "maxComponentsPerFile": 1 }
}
```

**역할 값 문법**

| 쓰는 값 | 뜻 |
| --- | --- |
| `"frontend-fundamentals:reviewer"` | 이 도구를 쓴다 |
| `["도구A", "도구B"]` | 둘 다 쓴다 (`review` 만 해당, 병렬) |
| `""` | 도구 없이 모델이 직접 한다 |
| 키를 안 씀 | 위 역할 표의 기본값을 쓴다 |

**단계를 아예 끄려면 `disable` 을 쓴다.** `""` 는 끄기가 아니다.
도구만 안 쓸 뿐 단계는 그대로 돈다.

**해석은 모델이 한다.** 훅(셸)은 `frontend-fundamentals:reviewer`가 에이전트인지
스킬인지 모른다. 훅은 트리거까지만 하고, 무엇으로 부를지는 `/lap`을 읽는 모델이
정한다. 이게 하드 의존성을 없애는 지점이다.

**`verify` 는 대부분 추론하지 않는다.** `format` 과 `lint` 만 prettier / eslint /
biome 를 찾아본다. 나머지는 **명시했을 때만** 돈다.
추측한 `test` 가 몇 분짜리 통합 테스트일 수도 있기 때문이다.

### 끄는 법

방해되면 끈다. **끌 방법이 없는 도구는 결국 삭제된다.**

```json
{ "disable": { "signals": true } }
```

`guide` · `format` · `lint` · `gate` · `verify` · `signals` · `loop` 을 각각 끌 수 있다.
자동 트리거만 시점별로 끄려면 `"trigger": { "commit": false }` 를 쓴다.
`jq` 가 없으면 플러그인 전체가 no-op 이 된다.

## 항상 도는 것 (루프 밖)

루프는 커밋 시점에 돌지만, 매 편집마다 도는 것도 있다.
**전부 신호이고 차단은 없다.**

| 훅 | 시점 | 동작 |
| --- | --- | --- |
| 포맷 | `Write`/`Edit` 후 | 편집된 파일 1개만 포맷 |
| 린트 피드백 | `Write`/`Edit` 후 | `--fix` 후 남은 문제를 **그 턴 안에** |
| 분량 신호 | `Write`/`Edit` 후 | 임계값 초과 시 경고 |
| 컴포넌트 신호 | `Write`/`Edit` 후 | 한 파일에 컴포넌트가 여럿이면 경고 |
| 품질 게이트 | 턴 종료 시 | 타입체크·테스트 실패면 **종료 차단** |
| 지침 주입 | 세션 시작 | 기준을 컨텍스트에 한 줄로 |

**포맷이 왜 필요한가**
Claude 가 `Write` 로 만든 파일은 에디터의 저장 이벤트를 안 거친다.
format-on-save 가 걸려 있어도 적용되지 않는다.

**린트가 왜 품질 향상인가**
타입 에러와 lint 에러는 취향이 아니라 **틀린 코드**다.
그리고 Claude 는 자기가 방금 만든 걸 그 자리에서 못 본다.
`PostToolUse` 의 stderr 는 그 턴 안에서 가므로 피드백이 분에서 초로 줄어든다.

**신호는 왜 쓴 뒤에 나오는가**
쓰기 전에는 정확히 셀 수 없고, 정확하지 않은 기준은 정상 코드를 막는다.
쓴 직후는 내용이 아직 컨텍스트에 있어 고치기 가장 싼 시점이다.

## 설계 판단

**왜 커밋이 루프의 경계인가**
한 가지 일이 끝나는 지점이고, diff 가 확정되고, 사람이 이미 멈추는 곳이다.
턴 단위는 경계가 될 수 없다. 오타 수정 턴과 리팩터링 턴에 같은 기준을 댈 수 없다.

**왜 `0` 과 "못 쟀다"를 구분하는가**
섞으면 도구가 죽었을 때 "중복이 사라졌다"고 보고하게 된다.
그래서 명령이 실패하면 `재지 못했습니다` 라고 낸다.
**없는 문제를 고치라고 하는 것이 막는 것보다 나쁘다.**

**왜 승격 카테고리를 고정하는가**
"같은 종류의 지적 3회"를 자연어로 판단하면 그때그때 달라진다.
오늘의 "가독성 문제"와 내일의 "읽기 어려움"이 같은 것인지 매번 다시 정하면
카운트가 안 쌓이고 **루프가 닫히지 않는다.**

**왜 개선을 자동 적용하지 않는가**
루프는 커밋 후에 돈다. 그 시점에 고치면 amend 나 후속 커밋이 필요하다.
무엇보다 이 리뷰가 믿을 만한지 아직 모른다.
신뢰가 쌓이면 `refine` 에 자동 적용 도구(내장 `simplify` 등)를 끼우면 된다.

**왜 신호 메시지에 끄는 방법을 안 적는가**
그 메시지는 사람이 아니라 Claude 가 읽는다.
끄는 법을 알려주면 신호를 끄는 쪽으로 갈 수 있어 README 에만 적는다.

**신호 임계값은 어디서 왔나**
감이 아니라 실측이다. `250` 은 새 파일이 만들어질 때 크기의 p95,
`80` 은 수정 커밋에서 추가되는 줄 수의 p96~97 이다.
저장소마다 분포가 달라 [`tools/measure-thresholds.sh`](tools/measure-thresholds.sh)
로 직접 재서 조정하는 걸 권한다.

## 알려진 한계

- **자동 트리거의 실사용 기록이 없다.** 동작은 검증했지만 매 커밋마다
  깨우는 게 성가신 수준인지는 아직 안 겪어봤다.
- **`learn` 의 실사용 기록이 없다.** 동작은 검증했지만 3회라는 기준과
  카테고리 목록이 맞는지는 아직 안 겪어봤다.
- **`guide` 역할이 미완이다.** 무엇을 주입할지는 `findings` 가 쌓인 뒤에 정한다.
- **a11y 는 정적 검사만 다룬다.** `eslint-plugin-jsx-a11y` 를 저장소 설정에
  넣도록 제안할 뿐이다. 대비 · 포커스 순서 같은 런타임 검사와 시맨틱 판단은 없다.
- **같은 컴포넌트를 감싸기만 한 경우도 2개로 센다.**
  `const Base = forwardRef(...)` 뒤에 `export const X = memo(Base)`. 오탐이다.
- **클래스 컴포넌트 미지원.**
- **한 턴 전체의 변경량은 보지 않는다.** 240줄짜리 파일 10개를 써도 신호가 안 난다.
- **`jq` 의존.** 없으면 전체 no-op.
- **Windows 는 WSL 기준으로만 확인.** macOS 기본 bash 3.2 에 맞춰 작성했다.
