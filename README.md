# fe-harness

Claude Code 자체가 에이전트 하네스다. 이 플러그인은 그 하네스에서
guardrails와 verification 레이어를 채운다 — 코드가 써지는 시점에
개입해서, 사람이 검토할 수 있는 크기로 유지한다.

🚧 **개발 중.** 설계와 근거: [docs/DESIGN.md](docs/DESIGN.md)

---

## 왜

Claude Code로 몇 주 작업하면 코드가 난잡해진다. 증상은 여러 개지만
원인은 하나다 — **Claude는 "지금 열려 있는 이 파일 안에서" 문제를 풀려고 한다.**

새 파일을 만드는 건 비싸고(위치를 정하고, import를 고치고, 구조를 알아야 한다)
현재 파일에 붙이는 건 공짜다. 그래서 한 파일이 계속 부푼다.

**처방: 새 파일 만들기를 싸게, 기존 파일에 붙이기를 비싸게 만든다.**

`CLAUDE.md`에 규칙으로 적으면 컨텍스트만 차고 준수율은 떨어진다.
강제 가능한 것은 훅으로 내린다. `PreToolUse` 훅은 권한 모드로도 우회되지 않는다.

## 지금 하는 일

### 구조가 무너지는 걸 막는다

| 훅 | 시점 | 동작 |
| --- | --- | --- |
| 분량 게이트 | `Write`/`Edit` 전 | 임계값 초과 시 **반려** |
| 인라인 컴포넌트 | `Write` 전 | 한 파일에 컴포넌트가 여럿이면 **반려** |
| 인라인 컴포넌트 | `Edit` 후 | 같은 상황을 **경고** |

**반려는 취소다.** 파일에 아무것도 안 써지고, Claude는 "대신 무엇을 하라"는
메시지를 읽고 다시 시도한다.

### 틀린 코드가 턴을 넘어가지 못하게 한다

| 훅 | 시점 | 동작 |
| --- | --- | --- |
| 린트 피드백 | `Write`/`Edit` 후 | `--fix` 후 남은 문제를 **그 턴 안에** 알림 |
| 품질 게이트 | 턴 종료 시 | 타입체크·테스트 실패면 **종료 차단** |

위의 두 게이트가 "구조 열화 예방"이라면 이 둘은 성격이 다르다.
**타입 에러와 lint 에러는 취향이 아니라 틀린 코드다.** 그리고 Claude는 자기가
방금 만든 걸 그 자리에서 못 본다 — CI가 몇 분 뒤에 알려준다.
`PostToolUse`의 stderr는 그 턴 안에서 간다. 피드백 루프가 분에서 초로 줄어든다.

**품질 게이트는 추론하지 않는다.** `.fe-harness.json`에 `typecheck`/`test`를
명시했을 때만 돈다. 차단하는 훅이 확신 없이 추론한 명령으로 개발을 막으면 안 된다.

### 나머지

| 훅 | 시점 | 동작 |
| --- | --- | --- |
| 규칙 주입 | 세션 시작 · 컴팩션 후 | 임계값을 컨텍스트에 한 줄로 넣음 |
| 포맷 | `Write`/`Edit` 후 | 편집된 파일 1개만 포맷 |

**규칙 주입이 유일한 예방 채널이다.** 훅은 반려밖에 못 하는데 그건 교정이다.
모델이 처음부터 제대로 쓰게 하려면 쓰기 전에 컨텍스트에 있어야 하고,
stdout이 컨텍스트로 가는 이벤트는 `SessionStart` 계열뿐이다.

**포맷이 왜 필요한가** — Claude가 `Write`로 만든 파일은 에디터의 저장 이벤트를
안 거친다. format-on-save가 걸려 있어도 적용되지 않는다. 포맷 안 된 코드가 섞인
diff는 사람이 검토할 수 없다.

## 설치

```bash
claude plugin marketplace add <이 저장소 경로 또는 URL>
claude plugin install fe-harness@fe-harness
```

설치 후 **반드시 확인한다**:

```bash
claude plugin list      # Status 가 실패가 아닌지
```

`claude plugin validate --strict` 통과와 로드 성공은 별개다. 매니페스트가
멀쩡해도 훅이 하나도 안 붙어 있을 수 있다.

## 설정

프로젝트 루트에 `.fe-harness.json`을 두면 **추론 없이 무조건 신뢰한다.**
없으면 추론하고, 추론도 실패하면 **조용히 통과한다.**
하네스가 확신 없이 뭔가 실행해서 개발을 막는 것보다 아무것도 안 하는 게 낫다.

전체 예시는 [`.fe-harness.example.json`](.fe-harness.example.json).

```json
{
  "maxNewFileLines": 250,
  "maxEditLines": 80,
  "maxComponentsPerFile": 1,
  "exclude": ["**/*.stories.tsx", "**/*.test.tsx", "src/gen/**"],

  "lint": "",
  "typecheck": "pnpm typecheck",
  "test": "",

  "inject": "",
  "guidance": ""
}
```

`format`과 `lint`는 비우면 prettier / eslint / biome을 추론한다.
`typecheck`와 `test`는 **추론하지 않는다** — 비워두면 품질 게이트가 돌지 않는다.

### 끄는 법

훅이 방해되면 끈다. 끌 방법이 없는 도구는 결국 삭제된다.

```json
{ "disable": { "guard": true } }
```

- `guard` — 반려하는 훅 (분량 · 인라인 컴포넌트)
- `format` — 포맷
- `warn` — 인라인 컴포넌트 경고
- `lint` — 린트 피드백
- `gate` — 품질 게이트 (`Stop`)
- `inject` — 규칙 주입

`jq`가 없으면 플러그인 전체가 no-op이 된다.

### `guidance`

반려 메시지 끝에 그대로 덧붙는 한 줄이다.

```json
{ "guidance": "쪼개기 전에 이 저장소의 컴포넌트 배치 규칙을 확인할 것" }
```

**플러그인은 당신이 어떤 리뷰 도구를 쓰는지 모른다.** 그 지식은 프로젝트
설정에만 둔다. fe-harness는 다른 어떤 플러그인도 요구하지 않고, 설치 여부를
확인하지도 않으며, 없어도 동작이 달라지지 않는다.

## 임계값의 근거

기본값은 감이 아니라 실측이다. 현업 저장소 5개에서 파일 생성 8,467건,
수정 24,976건을 쟀다 ([`tools/measure-thresholds.sh`](tools/measure-thresholds.sh)로 재현 가능).

| | p50 | p90 | p95 | p99 |
| --- | --- | --- | --- | --- |
| 파일이 처음 만들어질 때의 크기 | 49 | 174 | **244** | 437 |
| 수정 커밋에서 추가된 줄 수 | 4 | 33 | **59** | 163 |

`maxNewFileLines: 250`은 p95에 앉는다. `maxEditLines: 80`은 p96~97이다.

**저장소마다 분포가 다르다** — 생성 시 중앙값이 37~65로 갈렸다.
당신의 저장소에서 직접 재고 조정하는 걸 권한다.

```bash
tools/measure-thresholds.sh /path/to/your-repo
```

## 설계 판단과 포기한 것

**왜 저장소 전체가 아니라 파일 1개만 포맷하는가**
`PostToolUse`는 매 편집마다 돈다. 느리면 결국 끄게 된다.

**왜 새 파일과 기존 파일의 임계값이 다른가**
새 파일 만들기를 싸게, 기존 파일에 붙이기를 비싸게 만들려고. 그게 처방이다.

**왜 코드 품질 기준을 정의하지 않는가**
훅은 셀 수 있는 것만 판단한다. 줄 수와 컴포넌트 개수는 세지지만,
응집도나 이름이 동작과 맞는지는 읽어야 안다. 그건 리뷰 시점 도구의 몫이고,
같은 층위를 두 벌 얹으면 컨텍스트 비용이 두 배가 되고 충돌할 때
Claude가 임의로 하나를 고른다.

**왜 boolean prop 개수 경고가 없는가**
개수는 셀 수 있지만 그 개수가 문제인지는 읽어야 안다.
Button의 `disabled` + `loading`은 정상이다. 정상 코드에서 계속 뜨는 경고는
무시당하고, 결국 훅이 꺼진다.

**왜 자동 호출 스킬이 하나도 없는가**
전부 의도해서 부르는 작업이다.

**왜 반려 메시지에 끄는 방법을 안 적는가**
그 메시지는 사람이 아니라 Claude가 읽는다. 끄는 법을 알려주면
게이트를 끄는 쪽으로 갈 수 있다. 그래서 README에만 적는다.

## 다루지 않는 것

훅은 **셀 수 있는 것만** 판단한다. 아래는 원래 겪던 문제지만 이 플러그인이
대응하지 않는다. 리뷰 시점 도구나 사람의 몫이다.

- **"컴포넌트 하나가 너무 많은 일을 한다"** — 응집도 문제다. 200줄짜리가
  다섯 가지 일을 해도 그냥 통과한다. 줄 수는 이걸 재는 지표가 아니다.
- **중복** — 비슷한 유틸이 세 군데 생기는 걸 못 잡는다. 이건 저장소 전체를
  읽어야 알 수 있다.
- **한 턴 전체의 변경량** — 게이트는 도구 호출 하나의 크기를 본다.
  한 턴에 240줄짜리 파일 10개를 쓰면 전부 통과한다. 그리고 "쪼개서 각각
  Write 하라"는 반려 메시지가 오히려 턴 내 호출 수를 늘린다.
  적절한 턴 크기는 작업 종류마다 달라서 임계값이 존재할 수 없다고 판단했다.
- **아키텍처·패턴 선택, 이름, 추상화 수준** — 읽어야 아는 것이다.

## 알려진 한계

- **`Edit`으로 두 번째 컴포넌트를 끼워 넣는 경로는 반려가 아니라 경고다.**
  `PreToolUse`에서 `Edit`은 교체 조각만 주므로 파일에 컴포넌트가 몇 개가 될지
  알 수 없다. 정확히 세려면 파일이 써진 뒤여야 하고, 그때는 되돌릴 수 없다.
- **같은 컴포넌트를 감싸기만 한 경우도 2개로 센다.**
  `const Base = forwardRef(...)` 뒤에 `export const X = memo(Base)`. 오탐이다.
- **클래스 컴포넌트 미지원** (`class Foo extends Component`).
- **문서·설정 파일은 분량으로 막지 않는다.** 대상은 기본적으로
  `ts` `tsx` `js` `jsx` `mjs` `cjs` `vue` `svelte`. `extensions`로 조정한다.
- **`jq` 의존.** 없으면 전체 no-op.
- **Windows는 WSL 기준으로만 확인.** macOS 기본 bash 3.2에 맞춰 작성했다.
- **eval 하니스 없음.** 임계값과 문구가 실제로 효과가 있는지는 아직
  재현 가능한 방식으로 측정되지 않았다.
- **실사용 기록이 아직 적다.** 기본값들은 근거가 있지만, 오탐 빈도는
  충분히 관찰되지 않았다.

## 개발

```bash
./test.sh                      # 회귀 테스트
claude plugin validate . --strict
```

`hooks/scripts/lib-detect.sh`의 정규식을 고칠 때마다 `test.sh`를 돌린다.
새 오탐/미탐을 발견하면 그 코드를 `fixtures/`에 추가하고 기대값을 박는다.

훅을 직접 실행하는 게 디버깅에 제일 빠르다:

```bash
echo '{"tool_name":"Write","cwd":"'$PWD'","tool_input":{"file_path":"/tmp/a.tsx","content":"x"}}' \
  | ./hooks/scripts/guard-size.sh; echo "exit=$?"
```
