## 어느 루프인가

`$ARGUMENTS` 가 `push` 면 **외부 루프**, 비어 있으면 **내부 루프**다.

| | 내부 루프 (기본) | 외부 루프 (`push`) |
| --- | --- | --- |
| 자리 | **커밋 직후** | **푸시 직전** |
| 대상 | 아직 리뷰 안 된 최근 변경 | 브랜치 전체 |
| diff 범위 | 0단계가 정한다 | `origin/HEAD..HEAD` |
| 성격 | 빠르다. 증감만 | 비싸다. 전체 |

**루프를 섞지 않는다.** 내부 루프에서 전체 스캔을 돌리면 배경 잡음에 묻히고,
외부 루프에서 커밋 하나만 보면 브랜치가 남긴 상태를 놓친다.

---

## 역할 해석 — 모든 단계의 공통 규칙

각 단계는 `.fe-harness.json` 의 `roles.<역할>` 에 적힌 도구를 쓴다.

```
"이름"       그 도구를 호출한다. plugin:agent · plugin:skill · skill · /command
["a","b"]   여럿. review 만 병렬
""          도구 없이 직접 한다. 단계는 그대로 돈다
키 없음      README 역할 표의 기본값을 쓴다

역할에는 추론할 근거가 없다. 설치된 것 중에서 고르지 않는다 — 그건 v1 에서
사용자가 지정한 리뷰 도구를 안 쓴 사고의 원인이었다.
단계를 통째로 끄려면 `disable` 을 쓴다. `""` 는 끄기가 아니다.
```

**지정돼 있으면 반드시 그것을 쓴다.** 다른 걸로 대체하지 않는다. 호출에 실패하면
대체 실행하지 말고 **실패했다고 보고**한다 — 조용히 다른 걸 쓰면 사용자는 자기가
지정한 도구가 돈 줄 안다.

### 훅이 먼저 돌았을 때

이 절차는 두 경로로 들어온다 — 사람이 `/lap` 을 치거나, 커밋·푸시 훅이 깨우거나.

**훅이 깨운 경우 결정적 검사 결과가 이미 첨부돼 있다.** 그때는 **2단계를 다시
돌리지 않고 첨부된 결과를 그대로 쓴다.** 같은 명령을 두 번 돌리면 느리고,
그 사이 파일이 바뀌었으면 두 결과가 어긋난다.

**절차의 정의는 이 파일 하나뿐이다.** 훅은 방아쇠와 결정적 계산만 맡고
순서·역할 해석·판단을 갖지 않는다. 훅에 절차가 생기면 이 파일과 갈린다.

# 내부 루프 (기본)

**커밋 직후에 돈다.** 커밋을 대신 하지 않는다 — 사람이 커밋하면 그 변경을 본다.
아직 커밋하지 않았다면 아직 커밋 안 한 변경을 본다.

### 0 · 무엇을 볼지 정한다

```bash
git diff --quiet HEAD && base=HEAD~1 || base=HEAD
```

**미커밋 변경이 있으면 그게 이번 변경이고, 없으면 마지막 커밋이 이번 변경이다.**
어느 상태에서 불러도 *아직 리뷰 안 된 가장 최근 변경*을 보게 된다.
`git diff $base` 로 그 내용을 전부 읽는다. 볼 게 없으면 멈추고 그렇다고 말한다.

### 1 · verify — 정답이 있는 것

중복·죽은 코드는 **스크립트가 잰다.** 직접 명령을 조립하지 않는다:

```bash
${CLAUDE_PLUGIN_ROOT}/hooks/scripts/verify-scan.sh delta "$base"
```

**0단계에서 정한 `base` 를 반드시 넘긴다.** 기본값 `HEAD~1` 을 그대로 쓰면
아직 커밋 안 한 상태에서 직전 커밋의 변경까지 합산돼 **이번 변경이 늘리지 않은
중복을 이번 탓으로 보고한다.**

증감만 낸다. 변화가 없거나 잴 수 없으면 아무것도 출력하지 않는다 — 기존
저장소에 이미 중복이 200건이면 그 숫자는 행동으로 옮길 수 없다.

`verify.typecheck` · `verify.test` 는 설정돼 있으면 그대로 돌린다.
**`verify` 가 비어 있으면 조용히 건너뛴다.** 없는 명령을 추측해서 돌리지 않는다.

**a11y 정적 점검** — 이 저장소에 JSX 가 있는데 ESLint 설정에
`eslint-plugin-jsx-a11y` 가 없으면 **한 번만** 이렇게 제안한다:

> `eslint-plugin-jsx-a11y` 가 없습니다. `alt` 누락·잘못된 role·label 미연결 같은
> 접근성 문제를 작성 직후에 잡아 줍니다. 기존 CI 를 깨지 않도록 `warn` 으로
> 추가할까요?

**우리가 별도로 돌리지 않는다.** 저장소 설정에 들어가야 기존 lint 채널로 흐르고,
CI 와도 일치하고, 프로젝트가 룰을 조정할 수 있다. 사용자가 거절하면 다시 묻지 않는다.

### 2 · review — 읽어야 아는 것

**`roles.review` 를 쓴다. 이건 필수 역할이라 폴백이 없다.**
지정이 없으면 기본값 — `frontend-fundamentals:reviewer` 와
`a11y-specialist-skills:reviewing-a11y` 를 병렬로 쓴다. 축이 다르다:
앞은 코드 품질(응집도·가독성), 뒤는 접근성·시맨틱 마크업.

**diff 범위를 반드시 명시해서 넘긴다** — 리뷰 도구들의 기본값은 `main...HEAD` 라
그대로 두면 브랜치 전체를 본다. 여기서는 **`git diff $base`** 를 보라고 말한다.

**이번 변경이 한 가지 일인지도 본다.** 두 가지 이상이 섞여 있으면 그렇다고
알린다 — 아직 커밋 전이면 나눌 수 있고, 커밋 후라도 푸시 전이면 정리할 수 있다.

배열이면 병렬로 호출하고, 같은 곳을 가리키는 지적은 하나로 합친다.

### 3 · refine — 지적을 수정으로

리뷰 지적별로 **어떻게 고칠지**를 수정 코드까지 만들어 낸다.
`roles.refine` 에 도구가 지정돼 있으면 그것을 쓰고, 비어 있으면 직접 한다.

**묻지 않고 적용하지 않는다.** 커밋 후에 고치면 amend 나 후속 커밋이 필요하고,
무엇보다 이 리뷰가 믿을 만한지 아직 모른다. 사용자가 적용하라고 하면 그때 고친다.

미루는 게 맞는 지적은 **왜 미루는지 한 줄로 남긴다.**
고친 뒤에는 1단계 검사를 다시 돌려 깨지지 않았는지 본다.

### 4 · learn — 누적만

1·2단계 지적을 **스크립트로** 덧붙인다. 손으로 쓰지 않는다 — 형식이 흔들리면
카운트가 깨지고, 카운트가 깨지면 승격 제안이 안 나와 루프가 닫히지 않는다.

```bash
${CLAUDE_PLUGIN_ROOT}/hooks/scripts/findings.sh add <카테고리> "<요약>" <파일> <처리>
```

- **카테고리는 고정 목록에서 고른다** — `cohesion` `coupling` `predictability`
  `readability` `duplication` `deadcode` `a11y` `naming` `other`.
  "같은 종류"를 자연어로 판단하면 그때그때 달라진다. **필드 일치로 만들어야 센다**
- 처리는 `반영` 또는 `미룸:<이유>`. 미룰 거면 **왜 미루는지 반드시 남긴다**

**승격 제안은 여기서 하지 않는다.** 매 커밋마다 물으면 성가시다. 외부 루프 몫이다.

## 커밋과 PR 은 루프 밖이다

이 루프는 커밋을 만들지 않는다. 사람이 평소대로 커밋하고, 루프는 그 결과를 본다.
**커밋을 루프 안에 두면 커밋 훅이 발화해 루프가 두 번 돈다.**

다만 `roles.record` 에 도구가 있으면 커밋 메시지를 쓸 때 그것을 쓰고,
**아래 형식은 그 도구가 무엇이든 지킨다.**

```
<타입>: <50자 이내 요약>

<왜 이렇게 했는지. 3줄 이내.>
```

- 타입: `feat` `fix` `refactor` `docs` `test` `chore`
- **제목은 명사로 끝낸다.** `컴포넌트 개수 차단 폐기` (○) / `~를 폐기한다` (✗)
- **본문도 명사형으로 끝낸다.** `…판단은 review 에 위임.` `…로드에 실패하게 함.`
- **본문에는 "왜"만 쓴다.** "무엇을 바꿨는지"는 diff 가 말한다
- **금지**: 파일 목록, 변경 사항 불릿 나열, 단계별 설명
- 본문이 필요 없으면 제목만 쓴다. 대부분은 제목만으로 충분하다

한 줄로 안 써지면 커밋이 너무 큰 것이다. 나눈다.

### push 와 PR

푸시도 루프가 대신하지 않는다. 원격 기본 브랜치에 직접 push 하지 않고,
현재 브랜치가 기본 브랜치면 멈추고 사용자에게 확인받는다.

PR 본문도 커밋 메시지와 같은 원칙이다 — 짧게.

```
## 무엇을
<한두 문장>

## 왜
<한두 문장. 배경이나 결정 근거>

## 확인한 것
<어떻게 검증했는지 한 줄>
```

- **금지**: 변경 파일 목록, 커밋 단위 나열, 단계별 설명, 근거 없는 "테스트 완료"
- 리뷰어가 30초 안에 "무엇을 왜 했는지" 알 수 있어야 한다
- 길게 써야 이해되는 PR 이면 PR 이 너무 큰 것이다

# 외부 루프 (`/lap push`)

푸시 직전에 돈다. 내부 루프가 **구조적으로 못 보는 것**을 본다.

### 1 · 범위

`git diff origin/HEAD..HEAD` — 브랜치가 남긴 상태 전체.
푸시할 것이 없으면 멈추고 그렇다고 말한다.

### 2 · verify — 전체 스캔

- **전체 스캔** — `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/verify-scan.sh full`
  델타 검사는 커밋 A 와 커밋 C 사이에 생긴 중복을 못 본다 — 각 커밋 시점에는
  증가가 없기 때문이다. **여기서만 잡힌다.** 설정이 잘못돼 도구가 안 돌고
  있었다면 그것도 여기서 드러난다
- **`verify.a11yRuntime`** — 명시돼 있으면 돌린다. **비어 있으면 건너뛴다.**
  렌더 수단이 없다고 스토리북이나 E2E 를 만들라고 요구하지 않는다

### 3 · review — 브랜치 전체

`roles.review` 를 **범위를 넘기지 않고** 호출한다 — 도구의 기본값
(`main...HEAD`)이 여기서는 그대로 맞다.

커밋 단위 리뷰가 못 보는 것을 본다: 이 브랜치가 나눈 컴포넌트 경계가 맞는지,
여러 커밋에 걸쳐 생긴 중복이 있는지, 전체 구조가 말이 되는지.

**`findings.md` 에 이미 있는 지적은 다시 내지 않는다.**
같은 말을 두 번 들으면 사람은 루프를 끈다.

**다관점 리뷰를 붙인다면 여기다.** `roles.review` 가 배열이면 병렬로 호출한다.
내부 루프는 잦아서 비용과 잡음이 바로 체감되지만, 여기는 드물어서 감당된다.
단 **읽기만 하는 도구여야 한다** — 리뷰 중에 코드가 바뀌면 3단계 지적이 이미
반영된 코드를 가리키게 된다. 축이 겹치는 도구도 피한다. 같은 지적이 두 번 나온다.

기본값은 단독이다. 두 번째 렌즈가 실제로 새 지적을 내는지는 `findings` 를 봐야
알고, 아니면 토큰만 두 배 쓴다.

### 4 · learn — 승격 제안

**여기가 루프를 닫는 곳이다.**

```bash
${CLAUDE_PLUGIN_ROOT}/hooks/scripts/findings.sh count
```

같은 카테고리가 **3회 이상** 쌓였으면 승격 후보로 나온다. 아무것도 안 나오면
넘어간다 — 억지로 승격시키지 않는다.

후보가 있으면 `roles.learn` 에 지정된 도구(기본 `hookify`)로 규칙을 만들되,
**승격 경로는 지적의 성격이 정한다** — 스크립트 출력에 함께 나온다.

승격한 항목은 `findings.md` 의 처리 칸을 `승격:<수단>` 으로 바꾼다.
**그래야 다음 루프에서 다시 세지 않는다.** 한 번 제안하고 사용자가 미뤘는데
매번 다시 물으면 결국 끄게 된다.

**제안만 한다. 사용자 확인 없이 규칙을 추가하지 않는다.**

## 원칙

- **단계를 건너뛰지 않는다.** 특히 review — 이걸 건너뛰면 이 커맨드를 쓸 이유가 없다
- **플러그인 코드는 특정 도구 이름을 모른다.** 무엇을 쓸지는 `.fe-harness.json` 이 정한다
- **지정된 도구 호출에 실패하면 조용히 대체하지 말고 보고한다**
- **verify 는 추론하지 않는다.** 명시된 것만 돈다
- **외부 루프의 4단계가 이 루프의 이유다.** 매번 같은 지적을 받는다면 루프가
  도는 게 아니라 제자리걸음이다
