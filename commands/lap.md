## 어느 루프인가

`$ARGUMENTS` 가 `push` 면 **외부 루프**, 비어 있으면 **내부 루프**다.

| | 내부 루프 (기본) | 외부 루프 (`push`) |
| --- | --- | --- |
| 자리 | **커밋 직전** | **푸시 직전** |
| 대상 | 이번에 커밋할 변경 | 브랜치 전체 |
| diff 범위 | `HEAD` (스테이징 + 워킹) | `origin/HEAD..HEAD` |
| 성격 | 빠르다. **델타** | 비싸다. **전체** |

**루프를 섞지 않는다.** 내부 루프에서 전체 스캔을 돌리면 배경 잡음에 묻히고,
외부 루프에서 커밋 하나만 보면 브랜치가 남긴 상태를 놓친다.

---

## 역할 해석 — 모든 단계의 공통 규칙

각 단계는 `.fe-harness.json` 의 `roles.<역할>` 에 적힌 도구를 쓴다.

```
"이름"       그대로 호출한다. plugin:agent · plugin:skill · skill · /command
["a","b"]   여럿. review 만 병렬, 나머지는 순서대로
""          그 역할을 건너뛴다
키 없음      아래 각 단계의 폴백을 쓴다
```

**지정돼 있으면 반드시 그것을 쓴다.** 다른 걸로 대체하지 않는다. 호출에 실패하면
대체 실행하지 말고 **실패했다고 보고**한다 — 조용히 다른 걸 쓰면 사용자는 자기가
지정한 도구가 돈 줄 안다.

### 훅이 먼저 돌았을 때

이 절차는 두 경로로 들어온다 — 사람이 `/lap` 을 치거나, 커밋·푸시 훅이 깨우거나.

**훅이 깨운 경우 결정적 검사 결과가 이미 첨부돼 있다.** 그때는 **2단계를 다시
돌리지 않고 첨부된 결과를 그대로 쓴다.** 같은 명령을 두 번 돌리면 느리고,
그 사이 파일이 바뀌었으면 두 결과가 어긋난다.

**절차의 정의는 이 파일 하나뿐이다.** 훅은 방아쇠와 결정적 계산만 맡고
순서·역할 해석·판단을 갖지 않는다. 훅에 절차가 생기면 이 파일과 갈린다.

# 내부 루프 (기본)

### 1 · 범위 확인

`git diff HEAD` 로 이번에 나갈 변경을 전부 읽는다.
변경이 없으면 여기서 멈추고 그렇다고 말한다.

**이번 변경이 한 가지 일인지 본다.** 두 가지 이상이 섞여 있으면 커밋을 나눌 것을
제안하고 사용자 판단을 받는다.

### 2 · verify — 결정적 검사

`.fe-harness.json` 의 `verify` 에 **명시된 것만** 돈다. 추론하지 않는다.

- `verify.duplication` — 이번 변경이 중복을 **늘렸는지** 본다. 절대 수치가 아니라 델타다
- `verify.deadcode` — 이번 변경이 죽은 코드를 남겼는지
- `verify.typecheck` · `verify.test` — 설정돼 있으면

**비어 있으면 조용히 건너뛴다.** 없는 명령을 추측해서 돌리지 않는다.

**a11y 정적 점검** — 이 저장소에 JSX 가 있는데 ESLint 설정에
`eslint-plugin-jsx-a11y` 가 없으면 **한 번만** 이렇게 제안한다:

> `eslint-plugin-jsx-a11y` 가 없습니다. `alt` 누락·잘못된 role·label 미연결 같은
> 접근성 문제를 작성 직후에 잡아 줍니다. 기존 CI 를 깨지 않도록 `warn` 으로
> 추가할까요?

**우리가 별도로 돌리지 않는다.** 저장소 설정에 들어가야 기존 lint 채널로 흐르고,
CI 와도 일치하고, 프로젝트가 룰을 조정할 수 있다. 사용자가 거절하면 다시 묻지 않는다.

### 3 · review — 판단이 필요한 것

**`roles.review` 를 쓴다. 이건 필수 역할이라 폴백이 없다.**
지정이 없으면 `frontend-fundamentals:reviewer` 를 쓴다.

**diff 범위를 반드시 명시해서 넘긴다** — 리뷰 도구들의 기본값은 `main...HEAD` 라
그대로 두면 브랜치 전체를 본다. 내부 루프에서는 **`git diff HEAD`** 를 보라고 말한다.

배열이면 병렬로 호출하고, 같은 곳을 가리키는 지적은 하나로 합친다.

### 4 · refine — 수정안 제시

지적별로 **어떻게 고칠지**를 낸다. `roles.refine` 이 있으면 그것을 쓴다.

**자동으로 적용하지 않는다.** 무엇을 고칠지는 사용자가 정한다.
미루는 게 맞는 지적은 **왜 미루는지 한 줄로 남긴다.**

사용자가 고치기로 한 것을 반영한 뒤, 2단계 검사를 다시 돌려 깨지지 않았는지 본다.

### 5 · record — 커밋

`roles.record` 가 있으면 그것을 쓰되, **아래 형식은 그 도구가 무엇이든 지킨다.**
없으면 직접 쓴다.

```
<타입>: <50자 이내 요약>

<왜 이렇게 했는지. 3줄 이내.>
```

- 타입: `feat` `fix` `refactor` `docs` `test` `chore`
- **본문에는 "왜"만 쓴다.** "무엇을 바꿨는지"는 diff 가 말한다
- **금지**: 파일 목록, 변경 사항 불릿 나열, 단계별 설명
- 본문이 필요 없으면 제목만 쓴다. 대부분은 제목만으로 충분하다

한 줄로 안 써지면 커밋이 너무 큰 것이다. 1단계로 돌아가 나눈다.

### 6 · learn — 누적만

2·3단계 지적을 `.fe-harness/findings.md` 에 한 줄씩 덧붙인다. 파일이 없으면 만든다.

```
YYYY-MM-DD  <커밋 SHA>  <verify|review>  <지적 요약>  <파일>  <반영|미룸:이유>
```

**승격 제안은 여기서 하지 않는다.** 매 커밋마다 물으면 성가시다. 외부 루프 몫이다.

# 외부 루프 (`/lap push`)

푸시 직전에 돈다. 내부 루프가 **구조적으로 못 보는 것**을 본다.

### 1 · 범위

`git diff origin/HEAD..HEAD` — 브랜치가 남긴 상태 전체.
푸시할 것이 없으면 멈추고 그렇다고 말한다.

### 2 · verify — 전체 스캔

- **`verify.duplication` · `verify.deadcode` 를 전체 스캔으로** 돌린다.
  델타 검사는 커밋 A 와 커밋 C 사이에 생긴 중복을 못 본다 — 각 커밋 시점에는
  증가가 없기 때문이다. **여기서만 잡힌다**
- **`verify.a11yRuntime`** — 명시돼 있으면 돌린다. **비어 있으면 건너뛴다.**
  렌더 수단이 없다고 스토리북이나 E2E 를 만들라고 요구하지 않는다

### 3 · review — 브랜치 전체

`roles.review` 를 **범위를 넘기지 않고** 호출한다 — 도구의 기본값
(`main...HEAD`)이 여기서는 그대로 맞다.

커밋 단위 리뷰가 못 보는 것을 본다: 이 브랜치가 나눈 컴포넌트 경계가 맞는지,
여러 커밋에 걸쳐 생긴 중복이 있는지, 전체 구조가 말이 되는지.

**`findings.md` 에 이미 있는 지적은 다시 내지 않는다.**
같은 말을 두 번 들으면 사람은 루프를 끈다.

### 4 · push

`git push` 한다. 업스트림이 없으면 `-u` 로 명시적으로 설정한다.

원격 기본 브랜치에 직접 push 하지 않는다. 현재 브랜치가 기본 브랜치면
멈추고 사용자에게 확인받는다.

### 5 · PR

이미 열린 PR 이 있으면 만들지 않는다. 없으면 사용자에게 물어보고 만든다.

```
## 무엇을
<한두 문장>

## 왜
<한두 문장. 배경이나 결정 근거>

## 확인한 것
<어떻게 검증했는지 한 줄>
```

- **금지**: 변경 파일 목록, 커밋 단위 나열, 단계별 설명, 근거 없는 "테스트 완료"
- 리뷰어가 30초 안에 "무엇을 왜 했는지" 알 수 있어야 한다
- 길게 써야 이해되는 PR 이면 PR 이 너무 큰 것이다

### 6 · learn — 승격 제안

**여기가 루프를 닫는 곳이다.**

`.fe-harness/findings.md` 를 읽어 **같은 종류의 지적이 3회 이상** 반복됐는지 본다.
반복됐다면 매번 지적할 게 아니라 규칙이 되어야 한다는 뜻이다.

승격 경로는 지적의 성격이 정한다:

```
기계적으로 판정 가능   → hookify 규칙 (block / warn)
판단이 필요한 지침     → CLAUDE.md
이 저장소만의 맥락     → .fe-harness.json 의 guidance 한 줄
```

`roles.learn` 에 지정된 도구로 만든다. 지정이 없으면 `hookify` 를 쓴다.

**제안만 한다. 사용자 확인 없이 규칙을 추가하지 않는다.**

## 원칙

- **단계를 건너뛰지 않는다.** 특히 review — 이걸 건너뛰면 이 커맨드를 쓸 이유가 없다
- **플러그인 코드는 특정 도구 이름을 모른다.** 무엇을 쓸지는 `.fe-harness.json` 이 정한다
- **지정된 도구 호출에 실패하면 조용히 대체하지 말고 보고한다**
- **verify 는 추론하지 않는다.** 명시된 것만 돈다
- **외부 루프의 6단계가 이 루프의 이유다.** 매번 같은 지적을 받는다면 루프가
  도는 게 아니라 제자리걸음이다
