## 지금 상태

- 변경: !`git status --short`
- 열린 PR: !`gh pr list --head "$(git branch --show-current)" --json number,title 2>/dev/null || echo "-"`
- 브랜치: !`git branch --show-current`
- 최근 커밋: !`git log --oneline -5`

## 하는 일

커밋 직전 품질 루프를 순서대로 돈다. **각 단계를 건너뛰지 않는다.**
단계마다 결과를 한 줄로 보고하고 다음으로 넘어간다.

---

### 1 · 범위 확인

`git diff HEAD` 로 이번에 나갈 변경을 전부 읽는다.
변경이 없으면 여기서 멈추고 그렇다고 말한다.

**이번 변경이 한 가지 일인지 본다.** 두 가지 이상이 섞여 있으면
커밋을 나눌 것을 제안하고 사용자 판단을 받는다.

### 2 · 리뷰

**`.fe-harness.json` 의 `review` 에 지정된 도구를 쓴다.**

```json
{ "review": "frontend-fundamentals:reviewer" }
```

지정돼 있으면 **반드시 그것을 호출한다.** 다른 걸로 대체하지 않는다.
지정이 없으면 사용 가능한 스킬·에이전트 목록에서 코드 품질 리뷰에 해당하는
것을 골라 호출한다. 그것도 없으면 직접 읽고 검토한다.

직접 검토할 때 볼 것:

- 한 파일이 너무 많은 책임을 지고 있는가
- 한 파일에 컴포넌트가 여러 개 선언돼 있는가 — 특히 그 파일 안에서만 쓰는 것
- 이 상황에 맞는 컴포넌트 구조·패턴인가
- 이름이 하는 일과 맞는가, 읽으면서 되짚어야 하는 곳은 없는가

**지적을 목록으로 남긴다.** 4단계에서 쓴다.

### 3 · 개선

리뷰 지적 중 **지금 고쳐야 하는 것**을 고쳐 적용한다.

미루는 게 맞는 지적은 미루되 **왜 미루는지 한 줄로 남긴다.**
"나중에 하겠다"만 쓰고 넘어가지 않는다.

고친 뒤 타입체크·린트가 설정돼 있으면 다시 돌려 깨지지 않았는지 본다.

### 4 · 커밋

**메시지 형식을 반드시 지킨다:**

```
<타입>: <50자 이내 요약>

<왜 이렇게 했는지. 3줄 이내.>
```

- 타입: `feat` `fix` `refactor` `docs` `test` `chore`
- **본문에는 "왜"만 쓴다.** "무엇을 바꿨는지"는 diff 가 말한다
- **금지**: 파일 목록, 변경 사항 불릿 나열, 단계별 설명
- 본문이 필요 없으면 제목만 쓴다. 대부분은 제목만으로 충분하다

한 줄로 안 써지면 커밋이 너무 큰 것이다. 1단계로 돌아가 나눈다.

### 5 · push

`git push` 한다. 업스트림이 없으면 `-u` 로 명시적으로 설정한다.

원격 기본 브랜치에 직접 push 하지 않는다. 현재 브랜치가 기본 브랜치면
멈추고 사용자에게 확인받는다.

### 6 · PR

이미 열린 PR 이 있으면 만들지 않는다. 없으면 사용자에게 물어보고 만든다.

**PR 본문도 커밋 메시지와 같은 원칙이다 — 짧게.**

```
## 무엇을
<한두 문장>

## 왜
<한두 문장. 배경이나 결정 근거>

## 확인한 것
<어떻게 검증했는지 한 줄>
```

- **금지**: 변경 파일 목록, 커밋 단위 나열, 단계별 설명, 스크린샷 없는 "테스트 완료"
- 리뷰어가 30초 안에 "무엇을 왜 했는지" 알 수 있어야 한다
- 길게 써야 이해되는 PR 이면 PR 이 너무 큰 것이다

### 7 · 회고 — 루프를 닫는 단계

**2단계 리뷰에서 나온 지적을 `.fe-harness/findings.md` 에 한 줄씩 덧붙인다.**
파일이 없으면 만든다. 형식:

```
YYYY-MM-DD  <지적 요약>  <파일>
```

그리고 **그 파일을 읽어서 같은 종류의 지적이 3회 이상 반복됐는지** 본다.
반복됐다면 그건 매번 지적할 게 아니라 규칙이 되어야 한다는 뜻이다.
사용자에게 이렇게 제안한다:

> "`<지적>` 이 N회 반복됐습니다. 규칙으로 만들까요?"
> 선택지: `.fe-harness.json` 의 `guidance` 에 추가 / `CLAUDE.md` 에 추가 /
> 훅으로 강제 (hookify 가 설치돼 있으면 `/hookify` 로)

**제안만 한다. 사용자 확인 없이 규칙을 추가하지 않는다.**

---

## 원칙

- **단계를 건너뛰지 않는다.** 특히 2단계 리뷰 — 이걸 건너뛰면 이 커맨드를 쓸 이유가 없다
- **플러그인 코드는 특정 도구 이름을 모른다.** 어떤 리뷰 도구를 쓸지는 `.fe-harness.json` 이 정한다. 지정이 없으면 설치된 것 중에서 고르고, 그것도 없으면 직접 한다
- **7단계가 이 루프의 이유다.** 매번 같은 지적을 받는다면 루프가 도는 게 아니라 제자리걸음이다
