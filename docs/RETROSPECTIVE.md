# 회고 — 훅으로 코드 품질을 통제하려다 배운 것

> 2026-08-17 ~ 08-18. Claude Code 플러그인을 처음 만들면서 세운 명제를
> 실측으로 무너뜨리고 방향을 바꾸기까지의 기록.
>
> 결론부터: **동작하는 것과 쓸모 있는 것은 다르다.** 훅은 전부 의도대로
> 동작했다. 그런데 재보니 절반은 정상 코드를 막고 있었다.

---

## 1. 무엇을 만들려 했나

Claude Code로 몇 주 작업하면 코드가 난잡해진다. 증상은 여럿인데 원인은
하나로 보였다 — **Claude는 "지금 열려 있는 이 파일 안에서" 문제를 풀려고 한다.**

새 파일을 만드는 건 비싸고(위치 정하기, import 고치기, 구조 파악)
현재 파일에 붙이는 건 공짜다. 그래서 처방을 세웠다:

> **새 파일 만들기를 싸게, 기존 파일에 붙이기를 비싸게 만든다.**

그리고 이걸 `CLAUDE.md` 규칙이 아니라 **훅**으로 강제하기로 했다.
규칙은 컨텍스트만 차지하고 준수율은 떨어지지만, 훅은 결정적이니까.

---

## 2. 배운 것 — 플러그인 구성요소

이건 방향이 바뀌어도 남는 지식이다.

| 부품 | 실행 주체 | 결정성 | 컨텍스트 비용 | 차단 |
| --- | --- | --- | --- | --- |
| **hook** | 하네스가 실행하는 프로그램 | 결정적 | 0 | ✅ |
| **skill** | 모델이 읽는 지침 | 권고 | 호출 시 본문 전체 | ❌ |
| **agent** | 별도 컨텍스트의 모델 | 권고 | 메인 오염 없음 | ❌ |
| **command** | 사람이 부르는 진입점 | — | description만 상주 | ❌ |

### 훅에 대해 알게 된 것

**훅은 모델이 아니라 하네스가 실행한다.** 모델은 훅의 존재를 모른다.
그래서 "Claude가 규칙을 지킬까?"가 아니라 "프로그램이 돌았나?"의 문제가 된다.

**exit 2만 차단한다.** exit 1은 non-blocking error로 처리되고 그냥 진행된다.
그래서 `set -e`를 쓰면 안 된다 — 중간 실패가 exit 1로 나가서 차단이 조용히
통과된다.

**`PostToolUse`의 exit 2는 차단이 아니다.** 이미 써진 뒤라 되돌릴 수 없고,
stderr를 모델에게 보여주는 용도다. 화면에는 `hook blocking error`라고 뜨지만
파일은 이미 있다.

**stdout이 컨텍스트로 가는 이벤트는 셋뿐이다** — `SessionStart`,
`UserPromptSubmit`, `UserPromptExpansion`. 이게 중요한 이유는 뒤에 나온다.

### 스킬에 대해 알게 된 것 — 예방 채널이 아니다

스킬 본문은 **호출해야 로드된다.** 상주하는 건 `description` 한 줄뿐이다.
그래서 이런 순서가 된다:

```
쓴다 → 막힌다 → 스킬 로드 → 다시 쓴다      ← 교정
스킬 로드 → 쓴다                           ← 예방. 스킬로는 안 된다
```

예방을 하려면 **쓰기 전에 컨텍스트에 있어야** 하고, 그건 위의 stdout 세
이벤트로만 가능하다. **스킬은 "무엇을"을 담고, 훅은 "언제"를 담는다.**

### 훅과 스킬을 잇는 방법

훅의 stderr는 **모델이 읽는 프롬프트**다. 반려하면서 "이 스킬을 먼저 불러라"를
쓰면 훅이 트리거, 스킬이 판단이 된다.

단 **자기 플러그인에 있는 스킬만 가리켜야 한다.** 없는 이름을 쓰면 모델이
호출 실패로 한 턴을 버리거나, 더 나쁘게는 **이름만 보고 내용을 짐작해서
진행한다.**

## 3. 만든 것

훅 7개를 만들었고 전부 의도대로 동작했다.

| 훅 | 이벤트 | 하는 일 |
| --- | --- | --- |
| `format` | `PostToolUse` | 편집된 파일 1개만 포맷 |
| `guard-size` | `PreToolUse` | 분량 초과 시 반려 |
| `guard-components` | `PreToolUse` | 한 파일 컴포넌트 여럿이면 반려 |
| `warn-components` | `PostToolUse` | 같은 상황을 경고 |
| `lint-feedback` | `PostToolUse` | `--fix` 후 남은 것만 그 턴에 알림 |
| `gate-stop` | `Stop` | 타입체크·테스트 실패 시 종료 차단 |
| `reinject` | `SessionStart` | 임계값을 컨텍스트에 주입 |

**포맷이 왜 필요한가** — Claude가 `Write`로 만든 파일은 에디터의 저장 이벤트를
안 거친다. format-on-save가 걸려 있어도 적용되지 않는다.

## 4. 실측이 뒤집은 것

### ① 임계값 — 절반이 반대로 작동하고 있었다

처음 정한 값은 `새 파일 250줄 / 수정 150줄`이었다. 절대값만 보면
"새 파일은 넉넉, 수정은 빡빡"이라 처방대로다.

현업 저장소 5곳에서 **파일 생성 8,467건 · 수정 24,976건**을 쟀다:

| | p50 | p90 | p95 | p99 |
| --- | --- | --- | --- | --- |
| 생성 시 크기 | 49 | 174 | **244** | 437 |
| 수정 시 추가 | 4 | 33 | **59** | 163 |

```
새 파일 250줄 → p95    (상위 5%)     촘촘함
수정   150줄 → p98.5  (상위 1.2%)   헐렁함   ← 반대였다
```

**수정은 원래 작다. 중앙값이 4줄이다.** 한 번에 150줄을 붙이는 건 이미
예외적 사건이라 게이트가 사실상 안 걸렸다.

**측정 대상을 고르는 게 절반이었다.** 처음엔 현재 파일 크기 분포를 쟀는데
그건 틀린 비교였다 — 600줄 파일은 처음부터 600줄로 태어나지 않는다.
`--diff-filter=A`로 생성 시 크기를, `--diff-filter=M`으로 수정 시 추가분을
따로 재야 맞다.

### ② 컴포넌트 게이트 — 정상 코드의 5~31%를 막고 있었다

"한 파일에 컴포넌트 하나"는 그럴듯한 규칙이었다. 실제 `.tsx` 파일에 대보니:

| 저장소 | 컴포넌트 2개 이상 |
| --- | --- |
| A | 9.1% |
| B | **31.2%** |
| C | 4.7% |
| D | 12.8% |

그리고 막히는 것들이 **정당한 패턴**이었다:

- 아이콘 래퍼 **27개**를 모은 배럴 파일 — 27개로 쪼개면 더 나빠진다
- 본체와 함께 둔 표현용 래퍼 8개 — colocation이 오히려 읽기 좋다

스스로 세운 기준("정당하게 어겨야 하는 경우가 주 1회 이상이면 경고로 간다")을
압도적으로 위반한다. **이 게이트는 실사용 3일이면 꺼진다.**

### ③ 경계선을 잘못 그었다

품질 기준을 정의하지 않기로 하면서 선을 **"셀 수 있는가"**로 그었다.

그런데 컴포넌트 개수도 셀 수 있고, boolean prop 개수도 셀 수 있다. 문제는
**그 개수가 문제인지는 읽어야 안다**는 것이다. Button의 `disabled` + `loading`은
완벽하게 정상이고, 아이콘 27개도 정상이다.

**진짜 기준은 "틀렸는가, 아닐 수도 있는가"였다.**

```
객관적으로 틀림          → 차단   타입 에러 · lint 에러 · 테스트 실패
셀 수 있지만 판단 필요     → 신호   줄 수 · 컴포넌트 개수
읽어야 앎               → 리뷰   응집도 · 이름 · 패턴 선택
```

같은 원리를 두 번 발견하고 나서야 명시했다. 처음엔 flag props 경고를 이
이유로 지웠는데, **같은 결함을 가진 컴포넌트 게이트는 남겨뒀다.** 그것도
경고가 아니라 반려로.

## 5. 현업 저장소에 붙여봐야만 나온 것들

로컬 테스트 65개가 전부 통과하는 상태로 현업 모노레포에 붙였더니
`lint-feedback`이 **세 번 거짓말했다.** 셋 다 "코드에 린트 문제가 있다"고
보고했지만 전부 코드 문제가 아니었다.

1. **`--no-warn-ignored`는 ESLint 9 flat config 전용 플래그**였다.
   저장소는 eslintrc라 `Invalid option`으로 죽었다
2. **모노레포 루트에서는 eslint가 아예 안 돌았다.** 루트 설정이
   `@repo/eslint-config`를 참조하는데 루트에서는 해석이 안 된다.
   → 파일이 속한 패키지 디렉터리에서 돌려야 한다
3. **type-aware ESLint는 tsconfig include 밖 파일에 파싱 에러를 낸다.**
   Claude가 include 밖에 파일을 만드는 건 흔하다

> **훅이 낼 수 있는 최악의 출력은 차단이 아니라 거짓말이다.**
> 막히면 사람이 알아채지만, 없는 문제를 고치라고 하면 모델이 조용히 시간을 쓴다.

고친 뒤 규칙을 하나 세웠다 — **exit 1만 lint 문제로 취급한다.** ESLint는 2가
설정 오류다. 그 외 non-zero는 린터가 못 돌았다는 뜻이다.

### 그 외 몇 시간씩 날린 함정

**`hooks/hooks.json`은 자동으로 로드된다.** `plugin.json`에 또 적었더니
중복으로 잡혀 **플러그인 전체가 로드에 실패**했다. 그런데
`claude plugin validate --strict`는 이걸 통과시켰다.

> **validate 통과는 로드 성공이 아니다.** 설치 후 `claude plugin list`의
> `Status`를 반드시 확인해야 한다.

**문서 기록이 조용히 유실됐다.** 조정 기록 표를 `python .replace()`로
편집했는데 포매터가 표를 패딩해 문자열이 안 맞았다. `.replace()`는 못 찾아도
에러 없이 원본을 반환한다. **"기록했다"고 보고한 항목 12개가 전부 유실**돼
있었다. 커밋 전에 확인하지 않은 탓이다.

## 6. 왜 방향을 틀었나

### 목표가 조용히 좁혀져 있었다

원래 의도는 **"FE 코드 퀄리티 향상"**이었는데, 문서가 내건 목표는
**"변경을 검토 가능한 크기로 유지"**였다. 선을 긋는 순간 좁아졌는데
명시하지 않았다.

둘은 다른 물건이다. **제약 시스템**은 특정 실패 하나를 막고 끝나고,
**품질 루프**는 돌 때마다 축적된다.

### 만든 것을 목적에 대보니

| 원래 목적 | 달성 |
| --- | --- |
| 작업물 퀄리티 향상 | 부분 — 타입/lint 오류만 |
| 유지보수 가능 | 거의 없음 |
| **가독성** | **없음** |
| **만들고 → 리뷰받고 → 적용하는 과정** | **"만들고"만 있음** |

**원하는 건 루프인데 만든 건 문 하나였다.**

### 그리고 조각은 이미 다 있었다

공식 마켓플레이스를 뒤져보니 필요한 게 대부분 있었다.

| 필요한 것 | 이미 있는 것 |
| --- | --- |
| 커밋·PR 워크플로 | `commit-commands` |
| 코드 리뷰 | `code-review`, toss `frontend-fundamentals` |
| 코드 단순화 | `code-simplifier`, 내장 `simplify` |
| **대화 분석해서 훅 생성** | **`hookify`** |
| 타입 인텔리전스 | `typescript-lsp` |

특히 `hookify`는 "루프마다 피드백해서 규칙을 추가한다"는 요건 그 자체였다.
**"일반적이지 않을 것"이라고 판단했는데 틀렸다. 이미 성숙하게 있었다.**

없는 건 하나였다 — **언제 무엇을 어떤 순서로 쓸 것인가.**

---

## 7. 남은 방향

> **조각을 만들지 않고, 이미 잘 만들어진 것들을 엮어서 루프를 만든다.**

역할로 루프를 정의하고, 역할에 어떤 도구를 끼울지는 설정이 정한다:

```json
{
  "review":   "frontend-fundamentals:reviewer",
  "simplify": "simplify",
  "commit":   "commit-commands:commit",
  "rules":    "hookify"
}
```

이러면 **하드 의존성 없이** 있으면 활용하고, 갈아끼우는 것도 설정 한 줄이다.

그리고 훅은 사라지지 않는다. 역할이 바뀔 뿐이다 —
**차단이 아니라 루프의 체크포인트**로. "리뷰 없이 커밋하려 하면 막는다"처럼.

## 부록 — 블로그로 쓸 만한 것

1. **"측정 대상을 고르는 게 절반"** — 파일 크기 분포를 재면 안 되고
   생성 시 크기를 재야 했던 이야기
2. **"셀 수 있는가"가 아니라 "틀렸는가"** — 경계선을 두 번 잘못 긋고
   두 번 고친 이야기
3. **"훅의 최악은 차단이 아니라 거짓말"** — 현업 모노레포에서 세 번
   거짓말한 이야기
4. **validate 통과와 로드 성공은 다르다** — 매니페스트 한 줄로 플러그인
   전체가 죽은 이야기
5. **정상 코드의 31%를 막는 규칙** — 그럴듯한 규칙을 실제 코드에 대봤더니
6. **`.replace()`는 못 찾아도 에러를 안 낸다** — "기록했다"고 보고한 12건이
   유실돼 있던 이야기
