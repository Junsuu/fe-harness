## 1. 목적

만드는 사람이 쓰려고 만든다. 충족해야 할 것 7개:

1. FE 코드가 **가독성 · 유지보수 가능한 형태로 계속 발전**해야 한다
2. 한 파일에는 **컴포넌트 하나**. 그 안에서만 쓴다고 중첩으로 만들지 않는다
3. 상황에 **맞는 컴포넌트 설계 · 패턴**을 골라서 개발한다
4. 한 파일이 **너무 많은 책임**을 가지는 것을 막는다
5. **커밋 직전에 리뷰**하고, 개선점이 있으면 고친 뒤 커밋한다
6. **커밋 메시지 · PR을 요점만** 읽기 좋게 쓴다
7. **루프마다 피드백**해서 필요한 규칙 · 훅을 확인하고 필요하면 추가한다

7번이 이 도구가 존재하는 이유다. **루프는 돌 때마다 나아져야 한다.**
매번 같은 지적을 받으면 그건 루프가 아니라 제자리걸음이다.

## 2. 루프

```
        ┌──────────────────────────────────────────────┐
        │                                              │
   [0] 설계 ──▶ [1] 작성 ──▶ [2] 검증 ──▶ [3] 리뷰      │
                                            │          │
                                            ▼          │
   [6] 회고 ◀── [5] 커밋·PR ◀── [4] 개선 ───┘          │
        │                                              │
        └──── 반복된 지적 → 규칙으로 승격 ──────────────┘
```

| 단계 | 하는 일 | 누가 |
| --- | --- | --- |
| **0 설계** | 무엇을 어떤 구조로 나눌지 먼저 정한다 | 모델 (스킬) |
| **1 작성** | 코드를 쓴다 | 모델 |
| **2 검증** | 타입 · 린트 오류를 그 자리에서 잡는다 | 훅 (결정적) |
| **3 리뷰** | 판단이 필요한 것을 본다 | 기존 리뷰 도구 |
| **4 개선** | 지적을 실제 수정으로 옮긴다 | 모델 |
| **5 커밋·PR** | 요점만 담아 기록한다 | 커맨드 (형식 강제) |
| **6 회고** | 지적을 쌓고, 반복되면 규칙화를 제안한다 | 커맨드 + 누적 파일 |

**요건 대응**: 0→③ · 1→② · 2→① · 3→①④ · 4→① · 5→⑤⑥ · 6→⑦

## 3. 무엇을 만들고 무엇을 안 만드는가

**조각은 이미 생태계에 다 있다.** 없는 것은 **순서와 시점**이다.

| 단계 | 이미 있는 것 | fe-harness |
| --- | --- | --- |
| 0 설계 | `frontend-design`, `modern-web-guidance` | 트리거 |
| 2 검증 | 린터 · tsc · LSP | **호출과 시점** |
| 3 리뷰 | toss `frontend-fundamentals`, `code-simplifier`, 내장 `/code-review` | **강제** |
| 4 개선 | `simplify`, `code-simplifier` | — |
| 5 커밋·PR | `commit-commands` | **간결함 강제** |
| 6 회고 | `hookify`, `claude-md-management` | **누적과 승격 판단** |

### fe-harness가 소유하는 것 — 셋뿐이다

1. **순서** — 루프의 단계와 진행. `/ship` 커맨드
2. **체크포인트** — 건너뛰면 안 되는 지점의 강제. 훅
3. **누적** — 반복되는 지적을 규칙으로 올리는 판단. `findings` + 제안

### 만들지 않는 것

- **좋은 코드의 정의** — 리뷰 도구가 한다. 두 벌 얹으면 충돌한다
- **리뷰 실행** — 기존 에이전트가 한다
- **린터 · 타입체커** — 호출할 뿐 대체하지 않는다
- **규칙 자동 추가** — 제안까지만. 스스로 규칙을 늘리는 도구는 통제가 안 된다

### 의존성

**어떤 플러그인도 요구하지 않는다.** 리뷰 도구는 `.fe-harness.json`의
`review`가 지정하고, 지정이 없으면 설치된 것 중에서 고르고, 그것도 없으면
직접 검토한다. **플러그인 코드는 특정 도구 이름을 모른다.**

이 문서에 나오는 다른 플러그인 이름은 전부 **예시이자 참고**다.

## 4. 구성 요소 배치 규칙

| 부품 | 실행 | 결정성 | 컨텍스트 비용 | 차단 |
| --- | --- | --- | --- | --- |
| hook | 하네스가 실행 | 결정적 | 0 | ✅ |
| skill | 모델이 읽음 | 권고 | 호출 시 본문 전체 | ❌ |
| agent | 별도 컨텍스트 | 권고 | 메인 오염 없음 | ❌ |
| command | 사람이 호출 | — | description만 상주 | ❌ |

**선택 기준:**

```
객관적으로 틀림          → hook (차단)     타입 · 린트 · 테스트 실패
셀 수 있지만 판단 필요     → hook (신호)     줄 수 · 컴포넌트 개수
읽어야 앎               → skill / agent   응집도 · 이름 · 패턴 선택
사람이 시작점을 정함       → command        루프 진입
```

**"셀 수 있는가"가 아니라 "틀렸는가"로 가른다.** 컴포넌트 개수는 셀 수
있지만 그 개수가 문제인지는 읽어야 안다. 이걸 차단으로 두면 정상 코드를
막는다(부록 A).

**예방은 스킬로 안 된다.** 스킬은 호출해야 로드된다. 쓰기 전에 컨텍스트에
있어야 하는 것은 `SessionStart` stdout으로 주입한다 — stdout이 컨텍스트로
가는 이벤트는 `SessionStart` · `UserPromptSubmit` · `UserPromptExpansion`
셋뿐이다.

## 6. 설정

프로젝트 루트의 `.fe-harness.json`. **있으면 무조건 신뢰, 없으면 추론,
추론도 실패하면 조용히 통과.** 확신 없이 실행해서 개발을 막는 것보다
아무것도 안 하는 게 낫다.

전체 예시는 `.fe-harness.example.json`.

```json
{
  "review": "frontend-fundamentals:reviewer",
  "lint": "",
  "typecheck": "pnpm typecheck",
  "test": "",
  "disable": { "lint": false, "gate": false, "inject": false }
}
```

**`typecheck`와 `test`는 추론하지 않는다.** 차단하는 훅이 확신 없이 추론한
명령으로 개발을 막으면 안 되고, 추론한 test가 몇 분짜리일 수도 있다.

`disable`을 반드시 넣는다. 끌 방법이 없는 도구는 삭제된다.

## 7. 훅 작성 시 반드시 지킬 것

전부 이 프로젝트에서 실제로 겪은 것이다.

**exit 1은 차단하지 않는다.** exit 2만 차단한다. exit 1은 non-blocking
error로 처리되고 그냥 진행된다. 그래서 `set -e`를 쓰면 안 된다 —
중간 실패가 exit 1로 나가서 차단이 조용히 통과된다. `set -uo pipefail`만.

**`PostToolUse`의 exit 2는 차단이 아니다.** stderr를 모델에게 보여주는
것이다. 화면에는 `hook blocking error`라고 뜨지만 파일은 이미 써져 있다.

**`Stop` 훅은 `stop_hook_active` 파싱이 필수다.** 안 하면 무한 루프.
연속 8회 차단하면 무시된다.

**`hooks/hooks.json`은 자동으로 로드된다.** `plugin.json`에 또 적으면
중복으로 잡혀 **플러그인 전체가 로드에 실패한다.**

**`validate --strict` 통과는 로드 성공이 아니다.** 위 사고는 validate를
통과하고도 훅이 하나도 안 붙었다. 설치 후 `claude plugin list`의 `Status`를
반드시 확인한다.

**matcher는 unanchored다.** `Write|Edit`는 `NotebookEdit`에도 걸린다.
`^(Write|Edit)$`로 감싼다.

**모노레포에서는 파일이 속한 패키지에서 린터를 돌린다.** 루트 eslint 설정이
워크스페이스 패키지를 참조하면 루트에서는 해석이 안 된다.

**린터가 못 돈 것을 코드 문제로 보고하지 않는다.** ESLint는 1이 lint 문제,
2가 설정 오류다. exit 1만 lint 문제로 취급한다. type-aware ESLint가 tsconfig
include 밖 파일에 내는 에러도 코드 문제가 아니다.

> **훅이 낼 수 있는 최악의 출력은 차단이 아니라 거짓말이다.**
> 막히면 사람이 알아채지만, 없는 문제를 고치라고 하면 모델이 조용히 시간을 쓴다.

**stderr는 사람이 아니라 모델이 읽는다.** "Blocked"만 쓰면 우회를 시도한다.
"대신 무엇을 하라"를 반드시 넣고, 흔한 우회를 미리 막는다. **끄는 방법은
쓰지 않는다** — 모델에게 알려주면 게이트를 끄는 쪽으로 갈 수 있다.

**훅은 자기 플러그인의 스킬만 가리킨다.** 없는 스킬 이름을 쓰면 모델이
호출 실패로 한 턴을 버리거나, 이름만 보고 내용을 짐작해서 진행한다.

**성능** — `PostToolUse`는 매 편집마다 돈다. 편집된 파일 1개만 본다.

**`chmod +x`** 안 하면 조용히 실패한다.

### 디버깅

```bash
claude plugin list                    # Status 확인이 먼저
/hooks                                # 등록된 훅과 출처
claude --debug-file /tmp/claude.log

# 직접 실행이 제일 빠르다
echo '{"tool_name":"Write","cwd":"'$PWD'","tool_input":{"file_path":"/tmp/a.tsx","content":"x"}}' \
  | ./hooks/scripts/<훅>.sh; echo "exit=$?"
```

## 부록 A. 폐기한 설계와 이유

되풀이하지 않으려고 남긴다.

### 중심 명제였던 것 — "쓰기 직전 반려가 핵심"

`PreToolUse`에서 분량 · 컴포넌트 개수를 보고 반려하는 게 이 도구의 핵심이라고
설계했다. **실측으로 근거가 무너졌다.**

**컴포넌트 게이트(파일당 1개)** — 현업 저장소 4곳의 실제 `.tsx` 파일 중
**5~31%가 컴포넌트 2개 이상**이었다. 그리고 막히는 것들이 정당한 패턴이었다:
아이콘 래퍼 27개를 모은 배럴, 본체와 함께 둔 표현용 래퍼 8개. 스스로 세운
기준("정당하게 어겨야 하는 경우가 주 1회 이상이면 경고로 간다")을 압도적으로
위반한다.

**분량 게이트** — 250줄은 실측 p95에 정확히 앉아 4.5%만 걸렸고 실사용에서도
잘 작동했다. 근거가 약하지 않다. 다만 **재는 것이 "검토 가능성"이지
"품질"이 아니다.** 목적이 바뀌면서 주연에서 조연이 됐다.

**공통 오류** — 선을 **"셀 수 있는가"**로 그었다. 컴포넌트 개수도 셀 수 있지만
그 개수가 문제인지는 읽어야 안다. 진짜 기준은 **"틀렸는가, 아닐 수도 있는가"**다.
같은 이유로 flag props 경고도 폐기했다(`disabled` + `loading`은 정상이다).

### 목표가 조용히 좁혀져 있었다

원래 의도는 "FE 코드 퀄리티 향상"인데 문서가 내건 목표는 "검토 가능한 크기
유지"였다. 선을 긋는 순간 좁아졌는데 명시하지 않았다. **제약 시스템과 품질
루프는 다른 물건이다.**

### 증상 ①을 "해결"로 적었던 것

게이트는 도구 호출 하나의 크기를 볼 뿐 턴 전체를 안 본다. 240줄 × 10파일은
전부 통과한다. 게다가 "쪼개서 각각 Write 하라"는 반려 메시지가 턴 내 호출 수를
늘린다. **턴 단위 누적은 만들지 않는다** — 리팩터링 턴과 오타 수정 턴의 적정치가
달라 임계값이 존재할 수 없다.

### 문서 기록이 조용히 유실됐던 사고

조정 기록 표를 `python .replace()`로 편집했는데 포매터가 표를 패딩해 문자열이
안 맞았다. `.replace()`는 못 찾아도 에러 없이 원본을 반환한다. **"기록했다"고
보고한 항목 12개가 전부 유실**돼 있었다.
→ 표 대신 목록을 쓴다. 문서 편집 후 `grep`으로 반영을 확인한다.

## 부록 B. 실측 기록

**2026-08-18, 현업 저장소 5곳** (`tools/measure-thresholds.sh`로 재현 가능)

파일 생성 8,467건 · 수정 24,976건:

| | p50 | p75 | p90 | p95 | p99 |
| --- | --- | --- | --- | --- | --- |
| 파일 생성 시 크기 | 49 | 95 | 174 | 244 | 437 |
| 수정 시 추가 줄 수 | 4 | 12 | 33 | 59 | 163 |

**측정 대상을 고르는 게 절반이다.** 현재 파일 크기를 재면 안 된다 — 600줄
파일은 처음부터 600줄로 태어나지 않는다. `--diff-filter=A`로 생성 시 크기를,
`--diff-filter=M`으로 수정 시 추가분을 따로 재야 한다.

**컴포넌트 개수** — `.tsx` 파일 중 컴포넌트 2개 이상: 4.7% ~ 31.2% (저장소별).
