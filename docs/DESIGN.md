# fe-harness — 설계와 근거

> README 는 어떻게 쓰는지를 다룬다. 이 문서는 **왜 이렇게 만들었는지**를 다룬다.
> 개발 과정의 조정 기록과 회고는 저장소 밖에 보관한다.

---

## 왜 만들었나

Claude Code 로 프로젝트를 진행하면서 겪은 문제에서 출발했다 — 컴포넌트가
비대해지고, 중복이 생기고, 한 파일이 여러 역할을 지고, 가독성이 떨어진다.

처음(v1)에는 파일이 길어지는 게 원인이라 보고 쓰기 직전에 훅으로 막았다.
**실측으로 틀렸다.** 정상 `.tsx` 의 5~31% 가 컴포넌트 2개 이상이었고, 걸리는
것들이 아이콘 배럴처럼 정당한 패턴이었다. 길이는 증상이지 원인이 아니었다.

**원인은 만들기만 하고 되돌아보지 않는 것이다.** 그래서 v2 는 문(차단)이 아니라
바퀴(루프)다 — 커밋마다 검증·리뷰하고, 반복된 지적을 규칙으로 올린다.

## 명제 — 구현하지 않고 엮는다

마켓플레이스를 실사해 보니 필요한 조각은 대부분 이미 있었고 우리 것보다 나았다.
리뷰 기준(toss `frontend-fundamentals`), 규칙 생성(`hookify`), 커밋 워크플로
(`commit-commands`), 중복 탐지(`jscpd`), 죽은 코드(`knip`). 없는 것은
**언제 · 어떤 순서로 · 무엇을 부를 것인가** 하나였다.

그래서 fe-harness 는 도구가 아니라 **배선**이고, 소유하는 것은 셋뿐이다.

| 소유물 | 구현 | 왜 우리가 |
| --- | --- | --- |
| 역할 정의 | `.fe-harness.json` 의 `roles` | 도구는 자기가 루프의 어느 칸인지 모른다 |
| 트리거 | 커밋·푸시 훅 | 기억해서 부르는 건 결국 안 부른다 |
| 누적과 승격 | `findings` + 제안 | 반복된 지적을 규칙으로 올리는 판단 |

만들지 않는 것: 좋은 코드의 정의, 리뷰 실행, 린터·타입체커, 커밋 메시지 작성기,
규칙 자동 추가(제안까지만).

**없는 조각이 나타나면 별도 저장소의 독립 플러그인으로 만든다.** 루프 안에
싣는 순간 이 명제가 무너진다. 판정 기준은 하나 — *이 루프 없이 단독으로
설치해서 써도 말이 되는가.*

## 분류 축 — 설계 전체를 결정한 한 가지

```
프로그램이 판정할 수 있다   → verify   타입 · 린트 · 테스트 · 중복 · 죽은 코드
셀 수는 있지만 판단이 필요   → 신호만   파일 길이 · 컴포넌트 개수
읽어야 안다                → review   응집도 · 이름 · 패턴 · 시맨틱
```

중복과 죽은 코드가 `verify` 에 있는 게 핵심이다. 셀 수 있고 **동시에** 틀렸다고
단정할 수 있다 — 에이전트에게 시키면 부정확하고 비싸고, `jscpd` 가 세면 정확하고
싸다. 반대로 파일 길이는 셀 수 있어도 단정할 수 없다 — 데이터 테이블 · 타입
정의 · SVG 처럼 정당하게 긴 파일이 실재한다.

**그래서 차단하는 훅이 하나도 없다.** 세는 것은 신호로만 남기고, 그 개수가
문제인지는 review 가 읽고 판단한다. 신호가 `findings` 에 3회 쌓이면 루프가
차단 규칙(hookify) 승격을 제안한다 — **차단할지 말지를 우리가 짐작하지 않고
사용자의 데이터가 정한다.**

같은 축이 구현 곳곳에 재사용된다:

- `verify-scan.sh` — `0` 과 "못 쟀다"를 구분한다. 섞으면 도구가 죽었을 때
  "중복이 사라졌다"고 보고한다. **없는 문제를 고치라고 하는 것이 막는 것보다 나쁘다**
- `findings.sh` — "같은 종류 3회"를 자연어로 판단하면 매번 달라진다.
  카테고리를 고정해 필드 일치로 세게 만들어야 루프가 닫힌다
- `detect-project.sh` — "knip 이 있나" 같은 사실만 내고, "scripts.test 를
  Stop 게이트에 넣어도 되나" 같은 판단은 사람에게 묻는다

## 루프 구조

### 왜 커밋이 경계인가

한 가지 일이 끝나는 지점이고, diff 가 확정되고, 사람이 이미 멈추는 곳이다.
턴 단위는 경계가 될 수 없다 — 오타 수정 턴과 리팩터링 턴에 같은 기준을 댈 수 없다.

### 왜 두 개인가

비용이 다른 검사를 한 루프에 몰면 둘 다 못 쓴다.

| | 내부 (commit) | 외부 (push) |
| --- | --- | --- |
| 주기 | 잦다 | 드물다 |
| 대상 | 이번 커밋 | 브랜치 전체 |
| 중복·죽은 코드 | 델타 (증감만) | 전체 스캔 |
| 승격 제안 | 안 함 | 함 |

**외부 루프가 내부 루프의 구조적 한계를 메운다.** 델타 검사는 커밋 A 와 C
사이에 생긴 중복을 못 본다 — 각 커밋 시점에는 증가가 없기 때문이다. 승격
제안을 외부에만 둔 것도 같은 계산이다 — 매 커밋마다 물으면 성가시고,
성가시면 끈다.

델타여야 하는 이유: 기존 저장소에 이미 중복이 200건이면 절대값은 행동으로
옮길 수 없다. "이번에 3건 늘었다"만이 지금 고칠 수 있는 정보다.

### 왜 커밋 후에 도는가

자동화의 전부인 `asyncRewake` 가 `PostToolUse` 라 본질적으로 커밋 후다.
커밋 전에 잡으려면 `PreToolUse` 에서 막아야 하는데, 그게 v1 에서 폐기한 차단이다.
백그라운드로 돌아 사람의 턴을 막지 않는 것이 비싼 검사를 넣을 수 있는 이유이기도 하다.

기준 ref 는 커밋 여부로 판정한다 — 미커밋 변경이 있으면 `HEAD`, 없으면
`HEAD~1`. 어느 시점에 불러도 *아직 리뷰 안 된 가장 최근 변경*을 본다.

### 왜 refine 은 제안까지인가

루프는 커밋 후에 돈다. 그 시점에 자동으로 고치면 amend 나 후속 커밋이 필요하고,
무엇보다 이 리뷰가 믿을 만한지 아직 모른다. 신뢰가 쌓이면 `roles.refine` 에
자동 적용 도구(내장 `simplify` 등)를 끼우면 된다 — 그 전까지는 도구 없이
모델이 수정안을 만들고 적용 여부는 사람이 정한다.

`simplify` 를 review 에 넣지 않는 이유: 검토하면서 **고치기까지 해서** 리뷰가
부수효과를 갖게 되고, 단순화·추상화 축이 `frontend-fundamentals` 의 가독성·
응집도와 겹쳐 같은 지적이 두 번 나온다.

## 역할 해석

**해석은 모델이 한다.** 훅(셸)은 `frontend-fundamentals:reviewer` 가
에이전트인지 스킬인지 모른다. 훅은 트리거와 이름 전달까지만 하고, 무엇으로
부를지는 `/lap` 을 읽는 모델이 정한다. 이게 하드 의존성을 셸에서 없애는 지점이다.

**지정돼 있으면 반드시 그것을 쓴다.** 호출에 실패하면 대체 실행하지 말고
실패를 보고한다. v1 에서 "설치된 것 중 고른다"로 일반화했다가 사용자가 지정한
리뷰 도구를 안 쓴 사고가 있었다 — **역할에는 추론할 근거가 없다.** `verify.lint`
는 저장소의 린터 설정을 보고 추론할 수 있지만, 어떤 리뷰 기준을 원하는지는
저장소 어디에도 적혀 있지 않다.

**기본 조합이 이름을 부르는 외부 플러그인은 전부 `dependencies` 로 강제한다.**
기본값이 부르는데 없으면 그 역할이 조용히 비고, 그건 도는 척하는 것이다.
이 기준의 장점은 검증 가능성이다 — 기본 조합과 dependencies 두 목록을 diff
하면 끝난다. 대가는 "상대가 죽으면 우리도 죽는" 지점이 늘어나는 것이므로,
기본 조합에 도구를 추가하는 것은 가벼운 결정이 아니다.

서드파티에 버전 제약은 걸지 않는다 — 제약은 `{name}--v{version}` 태깅 규약에
의존하는데 남이 그걸 지킨다는 보장이 없고, 어기면 우리가 비활성화된다.

## 훅 구조 — 절차는 한 곳에만

훅 스크립트에 절차를 넣으면 셸 한 벌과 마크다운 한 벌이 되고, 둘은 반드시 갈린다.

```
loop-trigger.sh   방아쇠 + 결정적 계산(verify-scan)까지만
        ↓ asyncRewake
rewake 본문       "나머지는 /lap 절차대로" + 계산 결과 첨부
        ↓
모델              lap.md 를 읽고 review · refine · learn 수행
```

**절차의 정의는 `commands/lap.md` 하나. 진입점만 둘이다** — 사람이 치는
`/lap`, 훅이 깨우는 경로. 훅이 검사를 마치고 깨웠으면 모델은 같은 검사를 다시
돌리지 않는다 — 느릴 뿐 아니라 그 사이 파일이 바뀌면 두 결과가 어긋난다.

FE 파일이 안 바뀐 커밋은 깨우지 않는다. 문서 커밋에 FE 리뷰를 돌리는 건
토큰만 쓰고 잡음만 낸다.

## 설정 해석 — 3단 폴백

```
파일이 있다   그대로 쓴다. 추론하지 않는다
파일이 없다   린터·포매터만 추론한다
추론도 실패   아무것도 하지 않는다
```

확신 없이 뭔가 실행해서 개발을 막는 것보다 아무것도 안 하는 게 낫다.
`typecheck` · `test` · `duplication` · `deadcode` 는 추론하지 않는다 —
차단·비용이 걸린 검사가 추측한 명령으로 돌면 안 되고, 추측한 `test` 가
몇 분짜리 e2e 일 수 있다. 그래서 `/fe-harness:setup` 도 테스트 명령만은
반드시 사람에게 확인받는다.

옛 스키마(0.1.x 평면 키)는 폴백으로 읽지 않고 감지해서 알린다. 호환 계층은
회귀를 막는 대신 검증도 같이 막는다 — 폴백이 있는 동안 테스트 전부가 구
스키마를 쓰고 있었던 실례가 있다. **설정이 조용히 무시되는 것은 에러보다
나쁘다. 읽지 않을 거면 읽지 않는다고 말한다.**

같은 이유로 불리언 설정은 전용 함수(`fh_cfg_bool`)로 읽는다 — `jq` 의 `//` 는
`false` 를 "값 없음"으로 삼켜서, 끄려고 적은 `"commit": false` 가 조용히
무시된 버그가 실제로 있었다.

## 문구 원칙

- **훅의 stderr 는 사람이 아니라 모델이 읽는다.** "막았다"만 쓰면 우회를
  시도한다. "대신 무엇을 하라"를 넣고, 끄는 방법은 적지 않는다 — 그건 README 에만
- **안 막는 것을 막는다고 말하지 않는다.** 세션 주입 문구가 폐기된 차단을
  계속 안내하면 그게 곧 거짓말이고, 모델은 그 말을 믿는다
- **문서가 없는 동작을 설명하는 것은 훅이 없는 문제를 보고하는 것과 같은
  실패다.** 읽는 코드가 없는 설정 키는 문서에 쓰지 않는다

## 훅 작성 시 반드시 지킬 것

전부 이 프로젝트에서 실제로 겪은 것이다.

- **exit 2 만 차단한다.** exit 1 은 non-blocking. 그래서 `set -e` 금지,
  `set -uo pipefail` 만
- **`PostToolUse` 의 exit 2 는 차단이 아니다.** 모델에게 stderr 를 보여주는 것
- **`Stop` 훅은 `stop_hook_active` 파싱 필수.** 안 하면 무한 루프
- **`hooks/hooks.json` 은 자동 로드된다.** `plugin.json` 에 또 적으면 중복으로
  플러그인 전체가 로드 실패
- **`validate --strict` 통과는 로드 성공이 아니다.** `claude plugin list` 의
  `Status` 를 확인한다
- **matcher 는 unanchored.** `^(Write|Edit)$` 로 감싼다
- **모노레포는 파일이 속한 패키지에서 린터를 돌린다.** 루트 설정이 워크스페이스
  패키지를 참조하면 루트에서 해석이 안 된다
- **린터가 못 돈 것을 코드 문제로 보고하지 않는다.** ESLint 는 exit 1 만 lint
  문제다. 2 는 설정 오류
- **stdout 이 컨텍스트로 가는 이벤트는 셋뿐이다** — `SessionStart` ·
  `UserPromptSubmit` · `UserPromptExpansion`. 예방 주입은 여기로만 가능하다
- **훅은 자기 플러그인의 스킬만 가리킨다.** 없는 이름을 쓰면 모델이 짐작해서
  진행한다
- **`PostToolUse` 는 매 편집마다 돈다.** 편집된 파일 1개만 본다. 느린 훅은
  결국 꺼진다
- **`chmod +x`** 안 하면 조용히 실패한다
- 실행 환경은 **macOS 기본 bash 3.2.** 연관배열 · `${var^^}` 금지

### 디버깅

```bash
claude plugin list                    # Status 확인이 먼저
/hooks                                # 등록된 훅과 출처

# 직접 실행이 제일 빠르다
echo '{"tool_name":"Write","cwd":"'$PWD'","tool_input":{"file_path":"/tmp/a.tsx","content":"x"}}' \
  | ./hooks/scripts/warn-size.sh; echo "exit=$?"
```

## 결정 기록

1. **review 기본값은 2종 병렬** — `frontend-fundamentals:reviewer`(코드 품질) +
   `a11y-specialist-skills:reviewing-a11y`(접근성·시맨틱). 처음엔 단독이었으나
   축이 겹치지 않는 조각이 마켓에 생겨(2026-08-21 검증) 끼웠다. 같은 축을 두 벌
   얹는 것만 피한다 — 그건 같은 지적을 두 번 낸다
2. **refine 은 제안까지.** 근거는 위 「왜 refine 은 제안까지인가」
3. **트리거는 commit + push 이중 루프.** 비용이 다른 검사를 한 루프에 몰면
   둘 다 못 쓴다
4. **의존성으로 강제한다.** 조각을 엮는 도구가 조각 없이 조용히 도는 것은
   도는 척이다
5. **중복 · 죽은 코드는 verify.** 셀 수 있고 동시에 틀렸다고 단정할 수 있다
6. **a11y 는 세 계층.** 정적은 저장소 ESLint(`jsx-a11y` 추가 제안까지만),
   런타임은 외부 루프에서 저장소가 이미 가진 렌더 수단(E2E > 컴포넌트 테스트 >
   Storybook > 라우트 목록)에만 얹고, 판단(시맨틱 선택)은 review 의
   `a11y-specialist-skills` 가 맡는다
7. **차단하는 훅을 두지 않는다.** 분량 게이트는 실측 p95 에 앉아 잘 돌았지만,
   그것을 정당화하던 명제("새 파일은 싸게")가 폐기됐다. 근거가 철회된 장치를
   작동한다는 이유로 남기지 않는다

### 보류 — findings 가 쌓인 뒤에 정한다
