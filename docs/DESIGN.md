# fe-harness — 설계 v2 · 조합

> **fe-harness 는 조각을 만들지 않는다.**
> **역할로 루프를 정의하고, 역할에 무엇을 끼울지는 `.fe-harness.json` 이 정한다.**
> **엮은 조각은 `dependencies` 로 요구한다 — 없으면 동작하지 않는다.**
>
> 저자: tinyhex · 작성 2026-08-19 · 기준 Claude Code v2.1.220
> v1(제약 시스템)은 [`DESIGN-v1.md`](./DESIGN-v1.md), 그 과정은 [`RETROSPECTIVE.md`](./RETROSPECTIVE.md).

---

## 1. 문제

Claude Code 로 몇 주 작업하면 FE 코드가 이렇게 된다 — 컴포넌트가 비대해지고,
중복이 생기고, 한 파일이 여러 역할을 지고, 가독성이 떨어진다.

v1 은 원인을 **"파일이 길어지는 것"**으로 보고 훅으로 막았다. 실측으로 틀렸다는
게 드러났다(v1 부록 A·B). 길이는 증상이지 원인이 아니다.

**진짜 원인은 만들기만 하고 되돌아보지 않는 것이다.**

```
지금:   설계 → 작성 → 커밋 → 설계 → 작성 → 커밋 …     열화가 누적된다
필요:   설계 → 작성 → 검증 → 리뷰 → 개선 → 커밋 → 학습  개선이 누적된다
```

v1 은 이 그림에서 **문 하나**를 만들었다. v2 는 **한 바퀴**를 만든다.

### 증상을 성격으로 가른다

이 분류가 v2 설계 전체를 결정한다.

| 증상 | 성격 | 어느 역할 |
| --- | --- | --- |
| **중복 코드** | 결정적 — `jscpd` 가 정확히 센다 | **verify** |
| **죽은 코드 · 미사용 export** | 결정적 — `knip` | **verify** |
| **순환 의존 · import 규칙 위반** | 결정적 — `dependency-cruiser` | **verify** |
| **a11y 정적 위반** — `alt` 누락, 잘못된 role, label 미연결 | 결정적 — `eslint-plugin-jsx-a11y` | **verify** |
| **a11y 런타임 위반** — 대비, 포커스 순서, 탭 타깃 | 결정적이나 **렌더가 필요** | verify (조건부) |
| 타입 · 린트 · 테스트 실패 | 결정적 | **verify** |
| 파일 길이 · 컴포넌트 개수 | 셀 수 있으나 판단 필요 | **신호만 — 차단 없음** |
| **시맨틱 선택** — `div` 인가 `button` 인가, 제목 위계 | 읽어야 앎 | **review** + **guide** |
| 한 파일이 여러 역할 | 읽어야 앎 | **review** |
| 이름 · 구조 · 패턴 선택 | 읽어야 앎 | **review** |

**v1 이 놓친 것이 첫 세 줄이다.** v1 은 "셀 수 있는가"로 선을 그었다가 컴포넌트
개수를 차단에 넣는 실수를 했고, 그 반작용으로 **진짜 결정적인 것까지 판단 영역으로
밀어냈다.** 중복과 죽은 코드는 셀 수 있고 **동시에** 틀렸다고 단정할 수 있다.
이건 에이전트에게 시킬 일이 아니다 — 부정확하고 토큰이 비싸다.

## 2. 명제 — 조각은 이미 다 있다

로컬 마켓 5곳 전수 + 웹 조사 결과(5장) 필요한 조각은 **거의 전부 이미 있고,
대체로 우리보다 잘 만들어져 있다.** 리뷰 기준, 중복 탐지, 단순화 에이전트,
커밋 워크플로, 규칙 생성기까지.

없는 것은 **하나**다.

> **언제 · 어떤 순서로 · 무엇을 부를 것인가.**

그래서 fe-harness 는 도구가 아니라 **배선(wiring)** 이다. 소유하는 것은 셋뿐:

| 소유물 | 구현 | 왜 우리가 |
| --- | --- | --- |
| **역할 정의** | `.fe-harness.json` 의 `roles` | 도구는 자기가 루프의 어느 칸인지 모른다 |
| **트리거** | 훅 (커밋 시점) | 기억해서 부르는 건 결국 안 부른다 |
| **누적과 승격** | `findings.md` + 제안 | 반복된 지적을 규칙으로 올리는 판단 |

**만들지 않는 것:** 좋은 코드의 정의, 리뷰 실행, 린터·타입체커, 중복 탐지기,
커밋 메시지 작성기, 규칙 자동 추가(제안까지만).

## 3. 의존성 — 엮은 것이므로 요구한다

**v2 초안은 "어떤 플러그인도 요구하지 않는다"였다. 뒤집는다.**

fe-harness 는 조각을 만들지 않는다. 그런데 조각이 없어도 조용히 도는 도구라면,
그건 **아무것도 안 하면서 도는 척하는 도구**다. 배선만 있고 배선할 것이 없다.

Claude Code 는 v2.1.110 부터 플러그인 간 의존성을 지원한다.

```json
// .claude-plugin/plugin.json
{
  "name": "fe-harness",
  "version": "0.2.0",
  "dependencies": [
    { "name": "frontend-fundamentals", "marketplace": "toss" },
    { "name": "hookify",               "marketplace": "claude-plugins-official" },
    { "name": "commit-commands",       "marketplace": "claude-plugins-official" }
  ]
}
```

```json
// .claude-plugin/marketplace.json — 크로스 마켓 허용은 root 마켓이 연다
{
  "name": "fe-harness",
  "allowCrossMarketplaceDependenciesOn": ["toss", "claude-plugins-official"],
  "plugins": [{ "name": "fe-harness", "source": "./" }]
}
```

### 실측 — 2026-08-19, 0.1.0 → 0.2.0

선언한 대로 작동한다. **그리고 정말로 죽는다.**

```
claude plugin marketplace update fe-harness   # 로컬 마켓은 갱신해야 새 매니페스트를 읽는다
claude plugin update fe-harness@fe-harness    # 0.1.0 → 0.2.0, "+ 1 dependency: hookify"

  fe-harness@fe-harness  0.2.0  ✘ failed to load
  Error: Dependency "commit-commands@claude-plugins-official" is not installed
```

- **`hookify` 는 자동 설치됐는데 `commit-commands` 는 안 됐다.** 한 번에 다 해결된다고
  가정하면 안 된다. 에러 메시지가 정확히 어느 것이 빠졌는지 알려주므로 그대로 깔면 된다
- **로컬 디렉터리 마켓은 `marketplace update` 를 먼저 해야** 새 `plugin.json` 을 읽는다.
  안 하면 `already installed` 로 조용히 넘어가고 구 버전이 남는다
- 빠진 것을 설치하니 `✔ enabled` 로 돌아왔다

> **없는 플러그인을 `dependencies` 에 적지 않는다.** 선언한 의존성이 해결되지
> 않으면 `dependency-unsatisfied` 로 **fe-harness 자체가 비활성화된다.**
> 아직 만들지 않은 `a11y-semantics` 를 미리 적어두면 플러그인이 통째로 죽는다.
> **만든 뒤에 `dependencies` 와 기본 조합(6장)에 동시에 추가한다** — 둘 중
> 하나만 하면 규칙(기본 조합이 참조하는 것은 필수)이 깨진다.

### 이게 실제로 무엇을 강제하나

- **설치 시 자동으로 같이 깔린다.** `/plugin install fe-harness` 한 번이면 끝
  — **다만 실측에서는 한 번에 다 깔리지 않았다**(아래)
- **활성화하면 의존 플러그인도 같이 활성화된다**
- **없으면 `dependency-unsatisfied` 로 fe-harness 자체가 비활성화된다** — 이게 강제다
- **의존 플러그인을 혼자 끄려 하면 거부된다.** "fe-harness 가 아직 필요로 함"

### 대가 — 정직하게 적어둔다

| 대가 | 완화 |
| --- | --- |
| 사용자가 해당 마켓플레이스를 **먼저 추가**해야 한다. 안 하면 미해결로 남는다 | README 에 `claude plugin marketplace add` 두 줄을 최상단에 |
| 상대 플러그인이 죽거나 이름이 바뀌면 **우리도 같이 죽는다** | 서드파티에 버전 제약을 걸지 않는다(아래) |
| 무거워진다 — 리뷰 하나 쓰려고 4개가 깔린다 | **필수(hard)와 선택(soft)을 나눈다** |

### 필수와 선택을 나눈다

**기본 조합(6장)이 이름을 부르는 외부 플러그인은 전부 필수.**

기준을 "폴백이 있는가"로 잡아봤다가 되돌렸다. **폴백의 품질을 우리가 보증할 수
있는가**는 사람이 매번 판단해야 하는 기준이고, 판단이 들어가면 그때그때 달라진다.

지금 기준은 **검증 가능하다** — 기본 조합의 도구 이름과 `dependencies` 를
나란히 놓고 diff 하면 끝이다. 그리고 기본값이 부르는데 없어서 역할이 조용히
비는 상황, 즉 우리가 거부한 **"도는 척하는 도구"**가 구조적으로 불가능해진다.

| 역할 | 필수 여부 | `dependencies` | 이유 |
| --- | --- | --- | --- |
| **review** | **필수** | `frontend-fundamentals@toss` | 대체 수단이 "알아서 보기"뿐이다 |
| **learn** | **필수** | `hookify@official` | 승격 경로가 없으면 지적이 매번 반복된다 |
| **record** | **필수** | `commit-commands@official` | 기본 조합이 부른다 |
| **guide** | (위에 포함) | `frontend-fundamentals` 스킬 | 같은 플러그인이라 추가 의존성 없음 |
| **refine** | 불필요 | 내장 `simplify` | 내장이라 선언할 대상이 아니다 |
| **verify(중복)** | 불필요 | `npx jscpd` · `npx knip` | 플러그인이 아니라 CLI 다 |
| **review(a11y)** | 나중에 | `a11y-semantics@<별도 마켓>` | 존재하지 않는 동안은 양쪽 다 비워둔다 |

**대가를 알고 받는다** — 의존성 하나하나가 "상대가 죽으면 우리도 죽는" 지점이다.
셋으로 늘었다. 그래서 **기본 조합에 도구를 추가하는 것은 가벼운 결정이 아니다.**

### 버전 제약은 걸지 않는다

버전 제약은 git tag `{plugin-name}--v{version}` 규약에 의존한다. **서드파티가 이
규약대로 태깅한다는 보장이 없고**, 태그가 없으면 마켓의 현재 사본이 깔린 뒤
로드 시점에 제약을 검사해 **우리가 비활성화된다.** 그래서 서드파티 의존성은
전부 무제약(bare)으로 선언한다. 상대가 깨지면 그때 핀을 박는다.

## 4. 루프 — 어떻게 도는가

**루프는 하나가 아니라 둘이다.** 비용이 다른 검사를 한 루프에 몰면 둘 다 못 쓴다.

```
 ┌─ 작성 시점 (매 편집) ────────────────────────────────────────┐
 │  SessionStart ──▶ guide 주입 (한 줄)                          │
 │  PostToolUse  ──▶ format · lint(+a11y 정적)     [verify 즉시] │
 │  Stop         ──▶ typecheck · test              [verify 게이트]│
 └──────────────────────────────────────────────────────────────┘
                            │
                    git commit  ← 내부 루프 경계
                            │
 ┌─ 내부 루프 · 빠르다 (~1분) ▼─────────────────────────────────┐
 │  ① verify   jscpd · knip **델타**             결정적, 자동   │
 │  ② review   frontend-fundamentals (+a11y 는 나중)   이 커밋만 │
 │  ③ refine   수정안 제시 (적용은 사람)                          │
 │  ④ learn    findings.md 에 append                             │
 └──────────────────────────┬───────────────────────────────────┘
                            │  asyncRewake → 다음 작성 턴의 컨텍스트
                            │
                    git push  ← 외부 루프 경계
                            │
 ┌─ 외부 루프 · 비싸다 (~수 분) ▼───────────────────────────────┐
 │  ⑤ verify   a11y 런타임 (axe) · jscpd/knip **전체 스캔**      │
 │  ⑥ review   브랜치 전체 (main...HEAD)                         │
 │  ⑦ learn    findings 요약 → 3회 반복분 승격 제안               │
 └──────────────────────────┬───────────────────────────────────┘
                            │  asyncRewake → PR 올리기 전에 본다
                            ▼
```

### 왜 둘인가 — 비용과 대상이 다르다

| | **내부 루프** (commit) | **외부 루프** (push) |
| --- | --- | --- |
| 주기 | 잦다 | 드물다 |
| 시간 | ~1분 | 수 분 허용 |
| 대상 | **이 커밋의 diff** | **브랜치 전체** |
| 전제 | 없음 | 앱/스토리북이 뜰 수 있어야 |
| 성격 | 델타 — "이번에 3건 늘었다" | 전체 — "브랜치가 남긴 상태" |
| 놓치는 것 | 커밋 간에 걸친 중복 | 즉시성 |

**외부 루프가 내부 루프의 구조적 한계를 메운다.** 델타 검사는 커밋 A 와 커밋 C
사이에 생긴 중복을 못 본다 — 각 커밋 시점에는 증가가 없기 때문이다. 전체 스캔은
그걸 잡는다. 반대로 전체 스캔을 매 커밋에 돌리면 느리고, 기존 저장소의 배경
잡음(이미 있는 중복 200건)에 묻힌다.

### 내부 루프 (git commit)

**0. 트리거** — 사람이 `git commit` 을 친다. 커밋은 **이미 끝났다.** 훅은
`asyncRewake` 라 백그라운드로 돌고 사람의 턴을 막지 않는다.

**1. verify (결정적, ~5초)** — `verify-scan.sh delta` 가 `jscpd` · `knip` 을
**이전 커밋 대비 델타**로 잰다. 기준 커밋의 트리를 임시 디렉터리에 꺼내 같은
명령을 돌려 비교한다 — 사람이 작업 중인 워크트리는 건드리지 않는다.

**잴 수 없으면 아무것도 말하지 않는다.** 절대값을 대신 내지 않는다 — 기존
저장소에 이미 중복이 200건이면 그 숫자는 행동으로 옮길 수 없고, 그래서 애초에
델타를 택했다. 설정이 잘못돼 도구가 안 돌고 있었다면 외부 루프의 전체 스캔에서
드러난다.

**0 과 "못 쟀다"를 구분한다.** 이걸 섞으면 도구가 죽었을 때 "중복이 사라졌다"고
보고하게 된다 — v1 에서 린터로 세 번 겪은 그 실패다.

**2. review (판단, ~30초)** — `frontend-fundamentals:reviewer` 와
**`HEAD~1..HEAD` 범위를 명시해서** 부른다. 이 에이전트의 기본값은
`main...HEAD` 라 그대로 두면 브랜치 전체를 본다. (`a11y-semantics` 가 생기면
같은 배열에 붙고, 범위도 같이 넘긴다.)

**3. refine (제안만)** — 지적별로 "어떻게 고칠지"를 낸다. 적용하지 않는다(부록 A-2).

**4. learn (누적)** — `.fe-harness/findings.md` 에 한 줄씩 붙인다.
**승격 제안은 여기서 하지 않는다** — 매 커밋마다 물으면 성가시다. 외부 루프 몫.

### 외부 루프 (git push)

**5. verify (비싸다)** — 세 가지.
- **a11y 런타임** — `axe` 로 렌더된 DOM 을 검사한다(5장 ②). 앱/스토리북이 없으면 조용히 건너뛴다
- **`jscpd` · `knip` 전체 스캔** — 델타가 놓친 것을 잡는다
- 선택: 번들 크기 · 성능 회귀

**6. review (브랜치 전체)** — 범위를 넘기지 않고 **도구의 기본값
(`main...HEAD`)을 그대로 쓴다.** 커밋 단위 리뷰는 큰 그림을 못 본다 —
"이 브랜치가 컴포넌트를 3개로 나눴는데 경계가 이상하다" 같은 건 전체를 봐야 안다.
`code-review`(official)의 5에이전트 + 신뢰도 채점도 여기가 제자리다.

**7. learn (승격)** — 이번 브랜치의 `findings` 를 훑어 **3회 이상 반복된 것만**
승격을 제안한다(9장). 푸시당 한 번이라 빈도가 적절하다.

**중복 보고를 막는다** — 외부 루프는 `findings.md` 에 **이미 있는 지적을
다시 내지 않는다.** 같은 말을 두 번 들으면 사람은 루프를 끈다.

### 되돌리기 비용 — push 에 거는 것의 대가

앞서 `push` 를 트리거에서 뺐던 이유가 **"지적이 나와도 이미 올라간 뒤"**였다.
이 논리는 **코드 품질 리팩터링에는 유효하고 런타임 검사에는 약하다.**

- 리팩터링 지적은 amend 하고 싶어진다 → 올라간 뒤면 곤란
- **런타임 a11y 지적은 원래 후속 커밋 대상이다** → 올라간 것이 문제가 아니다

그래서 외부 루프의 성격은 **"고쳐라"가 아니라 "PR 올리기 전에 확인하라"**다.
push 와 PR 사이가 이 루프의 자리다.

### 작성 시점에는 무엇이 도는가

**아무것도 안 도는 게 아니다.** 다만 성격이 다르다.

| 시점 | v1 | v2 | 차이 |
| --- | --- | --- | --- |
| 세션 시작 | 임계값 주입 | **guide 주입** | 숫자 → 어디를 볼지 |
| 쓰기 직전 | **차단** (분량·컴포넌트) | **없음** | `PreToolUse` 훅이 하나도 없다 |
| 쓴 직후 | format · lint | format · lint · **분량·컴포넌트 신호** | 차단이 신호로 |
| 턴 종료 | typecheck · test 게이트 | 유지 | 유지 |
| **커밋** | **없음** | **루프 한 바퀴** | ← v2 의 전부 |

**작성 시점 개입을 버린 게 아니라, 차단을 버리고 주입을 남겼다.**
"이 파일 250줄 넘음, 반려" 대신 "구조를 정할 땐 이 스킬을 봐라" 한 줄이다.

이것으로 **충분한가**에 대한 판단은 부록 B 에 따로 적었다. 요약하면
**필요조건이지 충분조건이 아니다.**

## 5. 역할과 후보 — 마켓 + 웹 조사

로컬 마켓 5곳 전수(2026-08-19) + 웹 조사. **★ = 웹에서만 발견된 것.**

### verify — 결정적 검증

| 후보 | 성격 | 무엇 | 평가 |
| --- | --- | --- | --- |
| **`jscpd`** ★ | CLI | 복붙 블록을 결정적으로 탐지 | **1순위.** 사용자 증상 "중복"의 직답 |
| **`drywall`** ★ (nikhaldi) | plugin (MCP+skill+agent) | jscpd 를 감싸 랭킹·리팩터링까지 | 편하지만 무겁다. jscpd 직접이 더 쌀 수 있음 |
| **`knip`** ★ | CLI | 미사용 파일·export·의존성 | **1순위.** "한 파일 여러 역할"의 절반이 잔재다 |
| **`dependency-cruiser`** ★ | CLI | 순환 의존 · import 규칙 | 아키텍처 경계 강제용 |
| 기존 `lint-feedback` · `gate-stop` | hook | eslint · tsc · test | 유지 |

> **왜 에이전트가 아니라 CLI 인가** — DRYwall 저자의 지적이 정확하다:
> *"결정적 툴체인으로 중복을 탐지하기 때문에 에이전트에게 찾아서 리팩터링하라고
> 시키는 것보다 훨씬 효과적이고 토큰이 싸다."* 셀 수 있고 동시에 틀린 것은
> 세는 게 맞다.

### a11y · 웹 시맨틱 — 세 계층으로 나뉜다

**이 항목만 세 역할에 걸친다.** 한 덩어리로 다루면 반드시 틀린다.

| 계층 | 도구 | 시점 | 성격 | 처분 |
| --- | --- | --- | --- | --- |
| **① 정적** — JSX AST | **`eslint-plugin-jsx-a11y`** | **작성 직후** | 결정적 | **저장소 ESLint 설정으로 해소.** 우리는 점검·제안만 |
| **② 런타임** — 렌더된 DOM | `axe-core` (CLI/Playwright/Storybook) · 조사는 `chrome-devtools-mcp:a11y-debugging` ★ | **push** | 결정적이나 **렌더 필요** | **외부 루프에 넣는다** |
| **③ 판단** — 시맨틱 선택 | 없음 — 마켓에 조각이 없다 | 리뷰 | 읽어야 앎 | **나중에 스킬로 만들어 끼운다** |

#### ① 정적 — 여기가 이 프로젝트에서 가장 싼 개선이다

`eslint-plugin-jsx-a11y` 는 **그냥 ESLint 플러그인**이다. `lint-feedback` 훅이
이미 `PostToolUse` 마다 ESLint 를 돌리고 있으므로, **새 기계장치가 하나도 필요
없다.** 저장소 `eslint.config.js` 에 한 줄 추가하면 작성 직후 채널로 흘러든다.

```js
import jsxA11y from "eslint-plugin-jsx-a11y";
export default [jsxA11y.flatConfigs.recommended];
```

`alt` 누락, 잘못된 ARIA role, label 미연결, `<button>` 안의 `<button>`,
텍스트 없는 아이콘 버튼 — 전부 여기서 잡힌다.

> **v1 의 게이트와 무엇이 다른가.** v1 은 **우리가 임계값을 발명**했다(250줄,
> 컴포넌트 1개). 실측해 보니 절반이 반대로 작동했다. `jsx-a11y` 는 **남이 정한,
> 커뮤니티가 수년간 검증한 룰셋**이다. 우리가 정할 것이 없으므로 v1 의 실패
> 원인이 구조적으로 제거된다. **작성 시점 차단이 정당화되는 유일한 사례다.**

**fe-harness 가 하는 일은 점검과 제안까지다.** 플러그인은 저장소의 ESLint 설정에
들어가고, 검사 결과는 기존 `lint` 채널로 흐른다. 우리가 따로 부를 것이 없다.

**JSX 만 다룬다.** Vue·Svelte 용 대응물이 있지만 대상이 아니다.

##### 저장소 설정에 룰이 없으면 — 우리가 주입해서 돌릴 수 있나

**기술적으로는 된다.** fe-harness 에 `package.json` + 락파일을 두면 Claude Code 가
`npm ci --ignore-scripts` 로 플러그인 캐시에 설치해 주고, 별도 설정으로 돌릴 수 있다.

```bash
# ESLint 9. 저장소 설정을 전혀 읽지 않고 우리 설정만 쓴다
npx eslint --no-config-lookup --config "$CLAUDE_PLUGIN_ROOT/a11y.config.mjs" "$FILE"
```

**그런데 이건 v1 의 최악 실패 모드로 직행한다.**

| 문제 | 결과 |
| --- | --- |
| 프로젝트가 **의도적으로 끈 룰**을 우리가 다시 켠다 | 프로젝트가 "문제 아님"으로 결정한 것을 문제라고 보고 |
| eslint·파서 버전 불일치, tsconfig·JSX pragma 재현 실패 | 파싱 에러를 코드 문제로 보고 — **v1 에서 실제로 겪은 사고** |
| 린트 결과가 두 채널로 갈린다 | 저장소 lint 는 통과인데 우리만 빨갛다. 어느 쪽이 진짜인지 매번 판단 |
| CI 와 어긋난다 | 로컬에서만 잡히거나 그 반대 |

> **훅이 낼 수 있는 최악의 출력은 차단이 아니라 거짓말이다.**

**그래서 순서를 둔다.**

**1순위 — 설정에 추가를 제안한다.** 한 번 하면 끝나는 일이고, 그 뒤로는 기존
`lint` 채널로 그냥 흐른다. 새 기계장치 0, CI 와 일치, 프로젝트가 룰을 조정할
자유도 남는다. **기존 CI 를 안 깨뜨리도록 `warn` 으로 넣기를 함께 제안한다** —
도입 장벽이 사라진다.

**2순위 — 거부했거나 넣을 수 없을 때만 별도 실행.** 조건 셋을 반드시 지킨다.

- **차단하지 않는다.** 신호로만 내고 `findings` 에 쌓는다
- **출처를 명시한다** — "fe-harness 가 별도 설정으로 돌린 결과. 저장소 lint 와 다를 수 있다"
- **오탐 가능성이 낮은 부분집합만 켠다.** `recommended` 전체를 켜면 잡음이 된다

#### ② 런타임 — 외부 루프(push)에 넣는다

정적 분석은 최종 HTML 을 검사하지 못한다. 대비·포커스 순서·탭 타깃·실제
접근성 트리는 렌더해야 안다.

**커밋마다는 못 돌린다** — 수 분이 걸려 "커밋 한 번이 한 바퀴"를 깬다.
**push 는 드물고 사람이 이미 멈추는 지점이라 이 비용을 감당한다.**

##### 진짜 걸림돌은 트리거가 아니라 "무엇을 렌더할 것인가"다

push 가 일어난다고 개발 서버가 떠 있는 건 아니다. 그리고 diff 가
`Button.tsx` 를 건드렸을 때 **어느 화면이 그걸 렌더하는지 자동으로 알 방법이
없다.** 트리거를 옮겨도 이 문제는 그대로 남는다.

**원칙: 저장소가 이미 가진 렌더 수단에 얹는다. 없다고 만들라고 요구하지 않는다.**

| 방법 | 렌더 | 전제 | 잡히는 것 | 못 잡는 것 |
| --- | --- | --- | --- | --- |
| **E2E 안에 axe** (`axe-playwright`) | 실제 브라우저 | E2E 테스트 | **전부** — 로그인·데이터 로드된 실제 상태 | — |
| **컴포넌트 테스트 안에 axe** (`vitest-axe`) | jsdom | 단위 테스트 | 구조 · role · aria · label | **색 대비 · 탭 타깃** (jsdom 은 레이아웃·CSS 미계산) |
| Storybook (`test-storybook`) | 실제 브라우저 | **스토리 커버리지** | 스토리가 있는 것만 | 스토리 없는 화면 |
| 라우트 URL 목록 | 실제 브라우저 | 서버 기동 | 화면 전체 | 특정 상태 진입 |

**E2E 가 있으면 거기에 얹는 것이 가장 낫다.** 이미 실제 상태로 이동해 있으니
그 시점에 axe 를 주입하면 된다. Storybook 은 **스토리 커버리지가 있을 때만**
의미가 있다 — 전체에 스토리를 만들지 않는 저장소에서는 검사되지 않는 화면이
그대로 남는다.

**넷 다 없으면 이 계층은 이 저장소에서 감당이 안 되는 것이다. 만들지 않는다.**
스토리북이나 E2E 를 새로 만들라고 요구하는 것은 fe-harness 의 범위 밖이다.

> **그래도 외부 루프는 유지된다.** 외부 루프는 a11y 때문에 만든 게 아니다 —
> `jscpd`·`knip` 전체 스캔(커밋 간 중복), 브랜치 전체 리뷰, 승격 제안이
> 각각 독립적으로 그 자리를 정당화한다(4장).

##### Lighthouse 가 아니라 axe 다

`chrome-devtools-mcp:a11y-debugging` 스킬은 Lighthouse 감사부터 시작하라고
안내하는데, **Lighthouse 의 접근성 감사는 axe-core 의 부분집합**이다
(감사 57개 대 axe 룰 약 96개). Lighthouse 가 axe 보다 더 잡는 경우는 없다.

그리고 **조합 규칙 ④** 가 여기에도 적용된다 — 결정적인 것은 CLI 로.

```
verify(외부 루프)  axe CLI / test-storybook     결정적. 룰 ID 와 셀렉터가 나온다
   ↓ 조사가 필요할 때만
review/조사       chrome-devtools:a11y-debugging  포커스 순서 · 키보드 트랩 ·
                                                  탭 타깃 · 읽기 순서
```

즉 **에이전트로 매 push 마다 브라우저를 몰지 않는다.** CLI 가 먼저 재고,
CLI 가 판정할 수 없는 것(포커스가 모달에 갇히는가, DOM 순서가 시각 순서와
맞는가)만 스킬로 넘긴다. 이미 설치돼 있으므로 사람이 직접 불러도 된다.

#### ③ 판단 — 마켓에 조각이 없다. 만들어 끼운다

`frontend-fundamentals` **플러그인**은 4스킬(응집도·결합도·예측가능성·가독성)만
싣는다. toss 의 a11y 문서는 **웹사이트 쪽(`fundamentals/a11y/`)에만 있고 스킬로
패키징돼 있지 않다.** 내용은 좋다 — 4원칙과 그 아래 구체 사례:

```
① 올바른 구조      button 안의 button, 행 전체 클릭
② 의미 전달        인터랙티브 요소에 이름, 동명 요소 구분
③ 예측 가능한 동작  가짜 버튼(div+onClick), input 은 form 으로
④ 시각 의존 금지    이미지·아이콘 대체 텍스트
```

**조각이 없으면 만든다. 단 fe-harness 안에 만들지 않는다.**

```
✗  fe-harness 가 a11y 스킬을 싣는다        → "조각을 만들지 않는다" 붕괴
✓  a11y-semantics 를 독립 플러그인으로 만들고
   fe-harness 는 그것을 역할에 끼운다        → 정책 유지
```

**fe-harness 입장에서 이건 `frontend-fundamentals` 와 완전히 동일한 물건이다.**
`roles.review` 배열의 한 항목이고, 설정 한 줄로 갈아끼울 수 있고, 더 나은 a11y
스킬이 나오면 교체된다. 플러그인 코드는 여전히 특정 도구 이름을 모른다.

#### 진짜 별개인지 판정하는 기준

같은 사람이 만드니 **"fe-harness 의 사설 스킬이 옷만 갈아입은 것"**이 되기 쉽다.
판정 기준은 하나다:

> **fe-harness 없이 단독으로 설치해서 써도 말이 되는가.**

a11y 시맨틱 리뷰는 명백히 그렇다. 누구든 `/a11y-semantics` 로 자기 코드를 볼 수
있어야 하고, 그렇게 만들 수 없다면 그건 별개 플러그인이 아니라 위장이다.

#### 만들 때 지킬 것

| 지킬 것 | 이유 |
| --- | --- |
| **기준을 새로 정의하지 않는다.** toss a11y 4원칙 · web.dev · WCAG 를 가리키는 **얇은 포인터** | 정의를 만들기 시작하면 v1 로 돌아간다 |
| **①이 이미 잡는 것은 담지 않는다.** `alt` 누락, 잘못된 role, label 미연결은 ESLint 몫 | 중복하면 토큰 낭비이고 지적이 두 번 나온다 |
| **`frontend-fundamentals` 와 같은 모양으로 만든다** — 원칙별 skill + 이를 강제 로드하는 reviewer agent | 같은 모양이면 `review` 역할이 둘을 동일하게 다룬다 |
| **fe-harness 를 알지 못한다.** 설정·`findings` 를 참조하지 않는다 | 알기 시작하면 위장이 된다 |

즉 이 플러그인의 범위는 **"①이 못 잡는 것만"**으로 정확히 결정된다 — 정적 룰이
판정할 수 없는 시맨틱 **선택**의 영역이다. `<div onClick>` 대신 `<button>` 인가,
이 제목 위계가 문서 구조로서 말이 되는가, 이 랜드마크 배치가 맞는가.

#### 어디에 두나 — 별도 저장소

| | **별도 저장소** | 같은 저장소 · 별도 플러그인 |
| --- | --- | --- |
| 위장 위험 | **구조적으로 불가능** | 있음 — 판정 기준으로 막아야 |
| fe-harness 저장소 | **안 건드린다** (`source: "./"` 유지) | `fe-harness/` 로 옮겨야 → 캐시 갈림 |
| 독립 수명주기 | **있다** | 릴리스가 묶인다 |
| 남이 발견·사용 | **된다** | 하네스 안에 묻힌다 |
| 마켓 추가 | 하나 더 | 1개 |
| 크로스마켓 허용 | 우리 `marketplace.json` 에 한 줄 | 불필요 |
| 버전 핀 | 가능 (우리가 태깅) | 가능 |

**마켓 추가가 하나 느는 것은 새로운 종류의 비용이 아니다** — fe-harness 는 이미
`toss` 와 `claude-plugins-official` 을 요구한다. 세 번째가 는다고 성격이 바뀌지
않고, README 에 한 줄 더 적으면 된다.

**결정적인 것은 첫 줄이다.** 같은 저장소에 두면 "fe-harness 의 사설 스킬이 옷만
갈아입은 것"이 되기 쉽고, 그걸 막으려고 판정 기준을 세워야 했다. 저장소를 나누면
**지킬 규율이 아니라 구조가 된다.** fe-harness 의 설정도 `findings` 도 물리적으로
닿지 않는다.

```json
// fe-harness 의 marketplace.json — 만든 뒤에 한 줄 추가
{ "allowCrossMarketplaceDependenciesOn": ["toss", "claude-plugins-official", "<a11y 마켓>"] }
```

#### 시점 — 맨 마지막. 미루는 것이 선택지를 연다

**4·5번(verify 확장 · learn) 이후**다. 미루는 것은 게으름이 아니라 **세 갈래를
열어두는 것**이다.

| `findings` 가 말해줄 것 | 그때의 답 |
| --- | --- |
| 시맨틱 지적이 거의 없다 | **안 만든다.** ①로 충분했던 것 |
| 지적은 많은데 전부 ①이 잡을 수 있는 종류 | **ESLint 설정 문제였다.** 설정을 고친다 |
| 판단이 필요한 지적이 반복된다 | **만든다. 그리고 `findings` 가 그대로 목차가 된다** |

세 번째가 되면 스킬 내용이 **짐작이 아니라 실측 기반**이 된다. v1 이 짐작으로
임계값을 정했다가 절반이 반대로 작동한 것과 정확히 반대 절차다.

**그리고 그 사이에 마켓에 조각이 생길 수 있다.** 지금은 없다고 확인했지만 몇 달
뒤엔 다를 수 있고, 그러면 만들지 않는 것이 맞다. **미루는 것이 "조각을 만들지
않는다" 정책에 시간을 벌어준다.**

①만으로도 상당수가 걸린다 — 다만 **자동 도구가 잡는 것은 접근성 이슈 전체의
절반 남짓**이라 ③이 영영 없으면 나머지 절반이 통째로 빈다는 점은 기억해야 한다.

### review — 판단 리뷰

| 후보 | 성격 | 무엇 | 평가 |
| --- | --- | --- | --- |
| **`frontend-fundamentals:reviewer`** (toss) | agent (haiku) | 4스킬(응집도·결합도·예측가능성·가독성) 강제 로드 후 diff 리뷰 | **채택.** FE 전용, 기준이 문서로 존재 |
| `pr-review-toolkit` (official) | agent × 6 | `code-reviewer`(opus) · `silent-failure-hunter` · `type-design-analyzer` 등 | 다관점용. 오탐 필터를 우리가 만들어야 함 |
| `code-review` (official) | command | PR 전용. 5 에이전트 병렬 + 신뢰도 0~100 채점, 80 미만 폐기 | PR 단계용. 오탐 필터가 훌륭 |
| `hone-skills` ★ (ckorhonen) | skill × 8 | `duplication-hunt` · `naming-specificity-audit` · `broken-windows-hunt` · `magic-number-hunt` 등, **cadence 로 도는 설계** | **개념이 우리와 같다.** 스킬 단위로 골라 쓸 수 있음 |
| `coderabbit` · `sonarqube` · `greptile` | 외부 | 정적분석 | 팀 도입 시 |

> **`frontend-fundamentals:reviewer` 의 제약 2개** — ① 기본 diff 범위가
> `git diff main...HEAD` 다. 커밋 루프에서는 우리가 범위를 명시해 넘긴다.
> ② `model: haiku` 다. 부족하면 감싸지 말고 역할에 다른 도구를 끼운다.

> **스킬로는 예방이 안 된다.** 스킬 본문은 호출해야 로드된다. 쓰기 전에 있어야
> 하는 것은 stdout 이 컨텍스트로 가는 세 이벤트(`SessionStart` ·
> `UserPromptSubmit` · `UserPromptExpansion`)로만 넣을 수 있다.
> **guide = 훅이 "이 스킬을 먼저 불러라"를 주입하는 것.**

#### serena 는 역할이 아니다 — 능력이다

다른 후보들이 **"무엇을 하라"를 말하는 지침**이라면, serena 는 **"할 수 있게
만드는 도구"**다. 루프의 칸이 아니라 칸 전체의 전제다.

LSP 를 감싼 MCP 서버로, 텍스트가 아니라 **심볼 단위**로 코드베이스를 다룬다.

| 무엇을 주나 | 왜 이 루프에 중요한가 |
| --- | --- |
| `find_symbol` · `symbol_overview` · `find_declaration` | **중복 예방.** 이미 있는 걸 찾아야 안 만든다 |
| `find_referencing_symbols` · `type_hierarchy` | **영향 범위 파악.** "이거 고치면 뭐가 깨지나" |
| `replace_symbol_body` · `rename` · `safe_delete` | **refine 을 싸게 만든다.** 파일 간 rename 이 원자적 호출 하나 |

**왜 중복 예방에 직접 듣는가.** 지금 Claude 는 텍스트로 찾는다. 이미
`formatCurrency` 가 있어도 이름이 `toKRW` 면 grep 으로 못 찾고, 못 찾으면
**새로 만든다.** 심볼 인덱스는 이 실패를 줄인다. 실무 관찰에서도 시맨틱
인덱싱은 *"기존 코드를 찾고 기억해내는 능력을 확실히 개선한다"*고 평가된다
(부록 B ①).

**그리고 오탐이 없다.** 차단이 아니라 능력 부여이기 때문이다. v1 의 게이트가
정상 코드의 5~31% 를 막은 것 같은 실패 양식이 **구조적으로 불가능하다.**
부록 B 의 모델로 말하면 **열화 속도 `d` 를 줄이는 가장 안전한 수단**이다.

**대가** — MCP 서버라 무겁다. 프로젝트 인덱싱이 필요하고 툴 스키마가 컨텍스트를
먹는다(최근 Claude Code 는 MCP 툴을 지연 로드하므로 예전보다는 싸다).
그래서 **필수 의존성이 아니라 권장으로 둔다.** 효과는 4번 작업 후 중복 델타로
잰다 — 이 도구가 실제로 재는 능력을 갖게 되므로 검증이 가능하다.

### 조합하지 않는 것

`feature-dev`(루프와 범위 충돌) · `superpowers`(너무 큼) ·
`security-guidance`(보안. **다만 훅 패턴의 교과서 — 8장**) · `codex`(2차 의견).

## 6. 기본 조합

```json
{
  "roles": {
    "guide":  ["frontend-fundamentals:readability", "frontend-fundamentals:cohesion"],
    "__review": "a11y-semantics 는 만든 뒤에 배열에 추가한다. dependencies 와 동시에.",
    "review": "frontend-fundamentals:reviewer",
    "refine": "simplify",
    "record": "commit-commands:commit",
    "learn":  "hookify"
  },
  "verify": {
    "lint":        "",
    "typecheck":   "pnpm typecheck",
    "test":        "",
    "duplication": "npx jscpd --min-lines 8 --reporters json",
    "deadcode":    "npx knip --reporter json",

    "__a11yRuntime": "외부 루프 전용. 저장소가 이미 가진 렌더 수단을 여기 적는다. 비면 건너뛴다 — 없다고 만들지 않는다",
    "a11yRuntime": ""
  },
  "trigger": { "commit": true, "push": true },
  "disable": { "guide": false, "verify": false, "review": false }
}
```

**a11y 관련 키가 여기에 없는 것은 의도다.**

- **정적**은 저장소 ESLint 설정에 들어가 기존 `lint` 채널로 흐른다. fe-harness 가
  따로 부를 것이 없다 — `/lap` 이 빠져 있으면 추가를 제안하는 것까지만 한다
- **런타임**은 **외부 루프(push)** 에서 `axe` 로 돈다. 렌더 대상이 없으면 건너뛴다
- **판단**은 `roles.review` 배열의 한 항목이다. **fe-harness 가 싣는 게 아니라
  독립 플러그인을 끼우는 것**이라 `frontend-fundamentals` 와 취급이 같다

**설정 키가 안 늘어난 채로 세 계층이 다 배치됐다.** 아무도 안 켜는 키를 만들지
않는다 — v1 이 남긴 교훈은 안 쓰는 기계장치가 곧 삭제 대상이 된다는 것이다.

**`review` 가 유일하게 배열인 것도 규칙 ②와 일관된다** — 다관점은 이득이라는
예외다. 단 지적이 겹치기 시작하면 오탐 필터를 붙여야 한다.

**값 문법**

- `"도구 이름"` — 그대로 부른다. `plugin:agent` · `plugin:skill` · `skill` · `/command` 전부 가능
- `["a", "b"]` — 여럿. review 만 병렬, 나머지는 순서대로
- `""` — 그 역할 끄기
- 키 없음 — 추론한다. 실패하면 조용히 통과

**해석은 모델이 한다.** 훅(셸)은 `frontend-fundamentals:reviewer` 가 에이전트인지
스킬인지 모른다. 훅은 **트리거와 이름 전달**까지만 하고, 무엇으로 부를지는
`/lap` 을 읽는 모델이 정한다.

**`verify` 는 추론하지 않는다.** 차단하는 역할이 확신 없이 추론한 명령으로 개발을
막으면 안 되고, 추론한 `test` 가 몇 분짜리일 수도 있다. `lint`/`format` 만 추론한다.

## 7. 조합 규칙

**① 필수는 요구하고, 선택은 떨어뜨린다.**
`review`·`learn` 이 없으면 fe-harness 는 비활성화된다(3장). 나머지는
지정된 도구 → 설치된 것 → 모델이 직접 → 조용히 통과, 4단 폴백.

**② 한 역할에 두 벌을 얹지 않는다.**
좋은 코드의 정의를 두 개 얹으면 충돌한다. 예외는 `review` 뿐 — 다관점은 이득이다.
단 그때는 오탐 필터가 필요하다(`code-review` 의 신뢰도 채점을 차용).

**③ 지정이 있으면 반드시 그것을 쓴다.**
v1 에서 `/ship`(현 `/lap`) 이 "설치된 것 중 고른다"로 일반화하는 바람에 사용자가 원한 리뷰
도구를 안 쓴 사고가 있었다. **커플링 회피 원칙을 사용자 요건보다 앞세우지 않는다.**

**④ 결정적인 것은 CLI 로, 판단이 필요한 것만 에이전트로.**
중복·죽은 코드를 에이전트에게 시키면 부정확하고 토큰이 비싸다. 반대로 "이 이름이
하는 일과 맞나"를 정규식으로 재려 하면 v1 의 실수를 반복한다.

**⑤ 범위는 우리가 넘긴다.** 도구마다 기본 diff 범위가 다르다. 루프가 보는
범위(`HEAD~1..HEAD`)는 fe-harness 가 결정해서 명시한다.

**⑥ 끄는 방법을 반드시 만든다.** 끌 수 없는 도구는 삭제된다.

## 8. 트리거 — 왜 커밋이고, 어떻게 거는가

**커밋이 자연스러운 루프 경계다.** 한 가지 일이 끝나는 지점이고, diff 가 확정되고,
사람이 이미 멈추는 곳이다. 턴 단위는 경계가 아니다 — 오타 수정 턴과 리팩터링
턴에 같은 기준을 댈 수 없다.

### `asyncRewake`

공식 `security-guidance` 플러그인이 쓰는 훅 옵션이다. **`/lap` 을 사람이 기억해서
부르지 않아도 커밋 시점에 루프가 자동으로 돈다.**

```jsonc
// PostToolUse · matcher "Bash"
{
  "type": "command",
  "command": "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/loop-on-commit.sh",
  "if": "Bash(git commit:*)",           // 커밋 명령에만 발화
  "asyncRewake": true,                  // 백그라운드로 돌고
  "rewakeMessage": "커밋된 변경의 품질 루프 결과다. 반영하거나 이유를 남기고 계속:",
  "rewakeSummary": "커밋 리뷰에서 지적이 나왔다"
}
```

- 백그라운드라 **사람의 턴을 막지 않는다** — 커밋은 이미 됐고, 지적은 다음 턴에 온다
- 본문 채널은 **stderr + exit 2**. `Stop` 은 `hookSpecificOutput` 유니온에 없어서 그쪽으로 보내면 조용히 죽는다
- **`commit` 과 `push` 에 각각 다른 훅을 건다** — `if: "Bash(git push:*)"` 로 외부 루프를 깨운다. 같은 스크립트에 분기를 두지 않는다. 두 루프는 검사 항목도 diff 범위도 다르다
- `asyncRewake` 라 **외부 루프가 수 분을 먹어도 사람을 붙잡지 않는다.** 이게 비싼 검사를 루프에 넣을 수 있는 이유다

**이게 v1 과 v2 를 가르는 지점이다.** v1 의 훅은 *쓰기 직전에 막는* 문이었다.
v2 의 훅은 *커밋 시점에 루프를 깨우는* 초인종이다. **같은 부품, 반대 방향.**

### 훅과 `/lap` 은 절차를 나눠 갖지 않는다

훅이 붙으면 `/lap` 이 죽은 커맨드가 되거나, 더 나쁘게는 **훅 스크립트에 절차가
한 벌 더 생긴다.** 셸 한 벌과 마크다운 한 벌은 반드시 갈린다.

```
훅 스크립트      결정적인 것만 — jscpd · knip 델타 (셸로 가능한 부분)
    │ asyncRewake
    ▼
rewake 메시지    "나머지는 /lap 절차대로" + 위 결과 첨부
    ▼
모델             lap.md 를 읽고 review · refine · learn 수행
```

**절차의 정의는 `commands/lap.md` 한 곳뿐이다.** 훅은 방아쇠와 결정적 계산만
맡는다. 커맨드 파일은 모델도 `Skill("fe-harness:lap")` 로 부를 수 있으므로
**한 벌 정의에 진입점이 둘**이 된다 — 사람이 치는 `/lap`, 훅이 깨우는 경로.

**훅이 `jscpd` 를 돌리는 것은 복제가 아니다.** 훅도 `/lap` 도 `.fe-harness.json`
의 `verify.duplication` 에 적힌 **같은 명령**을 부른다. 무엇을 실행할지는 설정이,
어떤 순서로 무엇을 판단할지는 `lap.md` 가 소유한다. 훅은 어느 쪽도 갖지 않는다.

**단 두 번 돌지 않게 해야 한다.** 훅이 검사를 마치고 깨웠는데 모델이 `lap.md`
2단계를 그대로 따르면 같은 명령이 또 돈다. 느릴 뿐 아니라 그 사이 파일이 바뀌면
두 결과가 어긋난다. → `lap.md` 에 **"첨부된 결과가 있으면 다시 돌리지 않는다"**
를 명시했다.

### 훅이 있어도 사람이 직접 부를 이유

| 상황 | 왜 |
| --- | --- |

## 9. 누적과 승격 — 루프가 도는 증거

`verify` 와 `review` 의 지적을 `.fe-harness/findings.md` 에 한 줄씩 쌓는다.
**탭 구분 7칸**이고, `findings.sh` 가 형식을 고정한다.

```
날짜 ⇥ 커밋 ⇥ 출처 ⇥ 카테고리 ⇥ 요약 ⇥ 파일 ⇥ 처리
```

### 카테고리를 고정하는 것이 핵심이다

**"같은 종류의 지적 3회"를 자연어로 판단하면 그때그때 달라진다.** 오늘의 "가독성
문제"와 내일의 "읽기 어려움"이 같은 것인지 모델이 매번 다시 정한다. 그러면
카운트가 안 쌓이고, 승격 제안이 안 나오고, **루프가 닫히지 않는다.**

고정 목록에서 고르게 하면 셀 수 있는 값이 된다:

```
cohesion  coupling  predictability  readability     ← 리뷰 도구의 기준과 같은 축
duplication  deadcode  a11y  naming  other          ← verify 가 재는 것들
```

**새 축을 정의하지 않는다.** 앞의 넷은 `frontend-fundamentals` 의 4원칙 그대로다 —
리뷰가 그 기준으로 지적하는데 누적은 다른 축으로 하면 둘이 어긋난다.

### append 를 스크립트가 한다

모델이 손으로 쓰면 형식이 흔들린다. 탭 하나가 섞이면 필드가 밀리고 카운트가
깨진다. `findings.sh add` 가 탭·개행을 눕히고 날짜·SHA 를 채운다.

**이건 verify-scan.sh 와 같은 원리다** — 결정적으로 할 수 있는 것은 결정적으로.

### 한 번 제안한 것을 다시 묻지 않는다

승격한 항목은 처리 칸이 `승격:<수단>` 이 되고 카운트에서 빠진다.
**같은 것을 매 루프마다 물으면 사용자는 끈다.** 그리고 승격 이후 같은 카테고리가
새로 3회 쌓이면 다시 제안한다 — 규칙이 부족했다는 신호이기 때문이다.

같은 종류가 **3회** 반복되면 그건 매번 지적할 게 아니라 규칙이 되어야 한다는
뜻이다. 승격 경로는 셋이고, **어디로 올릴지는 성격이 정한다:**

```
기계적으로 판정 가능   → hookify 규칙   (block / warn)
판단이 필요한 지침     → CLAUDE.md      (claude-md-management)
이 저장소만의 맥락     → .fe-harness.json 의 guidance 한 줄
```

**제안만 한다.** 사용자 확인 없이 규칙을 추가하지 않는다.

### 이 도구가 작동하는지 아는 유일한 지표

**커밋당 신규 지적 수가 시간에 따라 줄어드는가.** 늘어나면 루프가 열화 속도를
못 따라가는 것이고, 그때는 작성 시점 개입을 늘려야 한다(부록 B).
`findings.md` 는 회고용이 아니라 **계기판**이다.

## 11. 훅 작성 시 반드시 지킬 것

전부 이 프로젝트에서 실제로 겪은 것이다. 상세는 [`DESIGN-v1.md` 7장](./DESIGN-v1.md).

- **exit 2 만 차단한다.** exit 1 은 non-blocking. 그래서 `set -e` 금지, `set -uo pipefail` 만
- **`PostToolUse` 의 exit 2 는 차단이 아니다.** 모델에게 stderr 를 보여주는 것
- **`Stop` 훅은 `stop_hook_active` 파싱 필수.** 안 하면 무한 루프
- **`hooks/hooks.json` 은 자동 로드된다.** `plugin.json` 에 또 적으면 플러그인 전체가 로드 실패
- **`validate --strict` 통과는 로드 성공이 아니다.** `claude plugin list` 의 `Status` 확인
- **matcher 는 unanchored.** `^(Write|Edit)$` 로 감싼다
- **모노레포는 파일이 속한 패키지에서 린터를 돌린다**
- **린터가 못 돈 것을 코드 문제로 보고하지 않는다.** ESLint 는 exit 1 만 lint 문제
- **훅은 자기 플러그인의 스킬만 가리킨다.** 없는 이름을 쓰면 모델이 짐작해서 진행한다
- **stderr 는 사람이 아니라 모델이 읽는다.** "대신 무엇을 하라"를 반드시 넣고, **끄는 방법은 쓰지 않는다**

> **훅이 낼 수 있는 최악의 출력은 차단이 아니라 거짓말이다.**

## 부록 A. 결정 기록

**2026-08-19 · 개발 착수 전.** 근거를 남긴다.

1. **`review` 는 `frontend-fundamentals:reviewer` 단독.**
   `pr-review-toolkit` 병렬은 커버리지를 늘리지만 오탐 필터를 우리가 만들어야
   한다. **부족하면 감싸지 말고 역할에 다른 도구를 끼운다** — 그러라고 만든 구조다.

2. **`refine` 은 제안까지.** 자동 적용은 이미 커밋된 코드를 바꿔 fixup 커밋을
   낳고, 잘못 고쳤을 때 되돌리기가 번거롭다. 무엇보다 **지적이 쓸모 있는지 아직
   모른다.** `findings` 가 쌓여 신뢰가 생기면 그때 다시 본다.

3. **트리거는 `commit` 과 `push` 둘 다 — 이중 루프.** (2026-08-19 갱신)
   처음엔 "`commit` 만, `push` 는 이미 올라간 뒤라 비싸다"로 정했다. **그 논리는
   리팩터링 지적에는 맞고 런타임 검사에는 약하다** — 런타임 a11y 지적은 원래
   amend 대상이 아니라 후속 커밋 대상이다.
   그리고 비용이 다른 검사를 한 루프에 몰면 둘 다 못 쓴다.
   → **내부 루프(commit): 빠르고 델타. 외부 루프(push): 비싸고 전체.**

4. **의존성은 선언해서 강제한다.** 조각을 만들지 않는 도구가 조각 없이도 조용히
   도는 건 도는 척하는 것이다. 대신 **필수(review·learn)와 선택을 나눠**
   무거워지는 것을 막는다. 서드파티에 **버전 제약은 걸지 않는다** — 태깅 규약을
   지킨다는 보장이 없고, 어기면 우리가 비활성화된다.

5. **중복·죽은 코드는 `review` 가 아니라 `verify` 다.** 셀 수 있고 동시에 틀렸다고
   단정할 수 있다. `jscpd`·`knip` 으로 결정적으로 잡는다. v1 은 "셀 수 있는가"로
   선을 잘못 그었고, 그 반작용으로 **진짜 결정적인 것까지 판단 영역으로 밀어냈다.**

6. **a11y · 웹 시맨틱은 세 계층이고, 각각 처분이 다르다.**
   - **① 정적 — 저장소 ESLint(`jsx-a11y`)로 해소.** JSX 만 다룬다. 기존 `lint`
     채널로 흘러들어 새 기계장치가 필요 없고, **우리가 임계값을 정하지 않으므로**
     v1 실패 원인이 구조적으로 없다. **우리가 플러그인을 주입해 별도로 돌리는
     것은 기술적으로 가능하지만 기본으로 삼지 않는다** — 프로젝트가 끈 룰을
     되살리고 파서 불일치로 거짓 보고를 낸다. 제안이 1순위, 별도 실행은
     차단 금지·출처 명시·부분집합 조건 아래 2순위
   - **② 런타임 — 외부 루프(push)에서 `axe` 로.** (2026-08-19 갱신) 커밋 루프엔
     못 넣지만 push 는 이 비용을 감당한다. **진짜 걸림돌은 트리거가 아니라
     렌더 대상**이라 Storybook 을 1순위로 두고, 없으면 명시된 URL, 둘 다 없으면
     건너뛴다. **Lighthouse 가 아니라 axe** — Lighthouse 감사는 axe 룰의
     부분집합(57 대 96)이라 더 잡는 경우가 없다.
     `chrome-devtools-mcp:a11y-debugging` 은 **CLI 가 판정 못 하는 것**
     (포커스 순서·키보드 트랩·읽기 순서)에만 쓴다 — 조합 규칙 ④.
     **렌더 수단은 저장소가 이미 가진 것에 얹는다**(E2E > 컴포넌트 테스트 >
     Storybook > 라우트 목록). **넷 다 없으면 이 계층은 만들지 않는다** —
     스토리북·E2E 를 새로 만들라고 요구하는 것은 범위 밖이다
   - **③ 판단 — `a11y-semantics` 를 별도 저장소에 만들어 마지막에 조립한다.**
     (2026-08-19 갱신) 마켓에 조각이 없으니 만들되 **fe-harness 안에도, 같은
     저장소에도 두지 않는다.** 저장소를 나누면 위장 위험이 지킬 규율이 아니라
     **구조**가 되고, fe-harness 의 `source: "./"` 도 안 건드린다.
     범위는 **기준을 정의하지 않는 얇은 포인터**, **①이 못 잡는 것만**.
     **시점은 맨 마지막이고 조건부다** — `findings` 가 필요를 증명해야 하고,
     그 사이 마켓에 조각이 생기면 만들지 않는다

7. **`serena` 는 필수 의존성이 아니라 권장.** 역할이 아니라 능력이고, 오탐이
   구조적으로 불가능해 열화 속도 `d` 를 줄이는 가장 안전한 수단이다. 다만 MCP
   라 무거워 강제하지 않는다. 효과는 4번 작업 후 **중복 델타로 잰다.**

### 아직 열린 것

- **`guide` 에 무엇을 넣을지** — 10장 7번대로 `findings` 를 보고 정한다.
- **`a11y-semantics` 를 만들지 말지 자체가 열려 있다.** 위치(별도 저장소)와
  범위("①이 못 잡는 시맨틱 선택만")는 정했지만, **만들 필요가 있는지**는
  `findings` 가 판정한다. 필요 없으면 안 만드는 것이 성공이다.

## 부록 B. "커밋 루프만으로 충분한가" — 판단

**질문:** 최초 작성 시점에는 개입하지 않고, 커밋마다 피드백해서 코드 컨텍스트를
건강하게 유지하면, 앞으로 쓰일 코드도 그 컨텍스트를 참고해 건강해질 것인가.

**답: 필요조건이지 충분조건이 아니다.** 근거를 나눠서 적는다.

### ① 가설의 맞는 부분 — 컨텍스트는 실제로 영향을 준다

모델이 주변 코드를 모방한다는 것 자체는 맞다. 다만 **조건이 하나 붙는다 —
모델이 그 코드를 읽어야 한다.** 읽지 않은 코드는 컨텍스트가 아니다.

여기서 실무 관찰 하나가 중요하다. 중복 대응 4가지를 순위 매긴
[nikhaldimann 의 글](https://ngof.nikhaldimann.com/p/4-ways-to-combat-claudes-code-duplication)은
**시맨틱 인덱싱(serena)이 "기존 코드를 찾고 기억해내는 능력을 확실히 개선한다"**고
평가한다. 즉 컨텍스트 가설이 작동하려면 **탐색 능력**이 전제다. 건강한 코드가
저장소에 있어도 못 찾으면 없는 것과 같다.

### ② 가설이 부족한 부분 — 예방만으로는 안 된다는 것이 이미 관찰됐다

같은 글의 결론은 명확하다. 예방책 3가지(찾기 쉬운 구조 · `CLAUDE.md` 지시 ·
시맨틱 인덱싱)로는 **불충분하고 사후 탐지가 필요하다.** 특히 `CLAUDE.md` 지시에
대해 저자는 *"그런 간단한 지시로 해결된다는 건 너무 좋은 얘기라 사실일 리 없다"*,
*"유사 로직이 있는지 확인하는 것은 근본적으로 어렵고 토큰이 비싸다"*고 적는다.

**이건 v2 를 지지하는 증거다.** 사후 루프는 반드시 필요하다.

### ③ 그런데 질문은 반대 방향이다 — 사후만으로 충분한가

여기서 열화를 **두 종류로 갈라야** 한다. 성질이 다르고, 사후 교정 비용이 다르다.

| | 누적형 열화 | 선택형 열화 |
| --- | --- | --- |
| 예 | 중복, 죽은 코드, 흩어진 상수, 비대해진 파일 | 구조·컴포넌트 경계·패턴·이름 선택 |
| 탐지 | **결정적** (jscpd, knip) | 읽어야 앎 |
| 사후 교정 비용 | **낮다** — 기계적 리팩터링 | **높다** — 사실상 다시 쓰기 |
| 커밋 루프로 | **충분하다** | **부족하다** |

**누적형은 커밋 루프로 충분하다.** 코드가 이미 있고, 결정적으로 측정되고,
고치는 게 기계적이다. 늦게 잡아도 손해가 작다.

**선택형은 다르다.** 잘못 고른 구조를 사후에 바꾸려면 새로 쓰는 것보다 비싸다.
그래서 실제로는 **미뤄지고**, 미뤄진 코드가 **다음 코드의 참조 대상이 된다.**
여기서 컨텍스트 가설이 역방향으로 작동한다 — 나쁜 컨텍스트가 나쁜 코드를 낳는다.

### ④ 발산 조건

루프가 커밋마다 `r` 만큼 고치고 작성이 커밋마다 `d` 만큼 나빠진다면,
`d > r` 인 동안 코드는 계속 나빠진다. **`r` 을 키우는 데는 한계가 있다** —
refine 을 제안까지로 정했고(부록 A-2), 사람이 다 반영하지 않는다.

그래서 실질적인 개선은 **`d` 를 줄이는 쪽**에서 나온다. 그게 작성 시점 개입이다.

### ⑤ 결론과 처방

**v1 의 실패는 "작성 시점에 개입한 것"이 아니라 "작성 시점에 차단으로 개입한
것"이었다.** 이 구분을 놓치면 v2 에서 작성 시점을 통째로 비우는 과잉 교정을 한다.

작성 시점에 필요한 것은 차단이 아니라 셋이다:

1. **탐색 능력** — `serena` / `typescript-lsp`. "이미 있는 걸 찾을 수 있어야 안
   만든다." 차단이 아니라 **능력 부여**라 오탐이 없다. 위 ①의 근거로 우선순위가 높다
2. **설계 선행** — 쓰기 전에 구조를 정하게 하는 주입(`think-first` 류).
   선택형 열화에 직접 듣는다
3. **기준 상주** — 리뷰와 **같은 기준**을 작성 전에 한 줄로 주입. 리뷰에서 지적할
   것을 쓰기 전에 알려주지 않으면 매번 같은 지적이 나온다

**단, 지금 다 만들지 않는다.** 무엇이 필요한지는 `findings.md` 가 말해준다 —
지적이 누적형에 몰려 있으면 루프로 충분하고, 선택형("구조를 잘못 골랐다",
"이 컴포넌트는 두 가지 일을 한다")이 반복되면 작성 시점 개입을 늘려야 한다.

**그래서 개발 순서가 `verify 확장(4) → learn(5) → guide(7)` 이다.**
guide 를 마지막에 두는 건 미루는 게 아니라, **무엇을 넣을지 짐작하지 않기
위해서**다. v1 이 짐작으로 임계값을 정했다가 절반이 반대로 작동했다.

## 부록 C. 조정 기록

**루프가 도는 증거가 여기 쌓인다.** 기준은 하나 — **거슬린 순간.** 특히
**"이거 그냥 끄고 싶다"**는 생각이 든 순간은 반드시 적는다.

### 2026-08-19

**v1 설계를 조합 중심으로 전면 교체했다.**
마켓 실사에서 필요한 조각이 거의 전부 이미 있다는 것과, `asyncRewake` 로 커밋
시점에 루프를 자동으로 깨울 수 있다는 것을 확인했다.
→ 훅의 역할을 "차단하는 문"에서 "루프를 깨우는 초인종"으로 바꿨다.

**"어떤 플러그인도 요구하지 않는다"를 뒤집었다.**
커플링 회피를 원칙으로 세웠는데, 조각을 만들지 않는 도구가 조각 없이도 도는 건
도는 척하는 것이었다. v1 에서 `/ship`(현 `/lap`) 이 리뷰 도구를 일반화했다가 요건을 놓친
사고와 **같은 실수의 반복**이다.
→ `dependencies` 로 필수를 강제하고, 필수와 선택을 나눴다.

**a11y · 시맨틱을 아예 빠뜨리고 있었다.**
"다시 코드를 손대는" 실제 재작업의 큰 몫이 여기서 나왔는데 v1·v2 초안 어디에도
없었다. 시맨틱 마크업은 **구조적 선택**이라 사후 교정 비용이 크다 —
`<div onClick>` 을 `<button>` 으로 바꾸면 이벤트·포커스·키보드·스타일 리셋이
전부 딸려 온다. 부록 B 가 말한 **선택형 열화의 가장 선명한 사례**다.
→ 세 계층으로 나누고, 정적 계층을 개발 순서 0번으로 올렸다.

**"조각을 만들지 않는다"를 두 번 연속 잘못 다뤘다.**
한 번은 **과잉 적용** — a11y 판단 계층에 조각이 없다는 걸 확인해 놓고도 원칙
때문에 "열어둔다"로 미뤘다. 원칙은 *"이미 있는 것을 다시 만들지 않는다"*인데
*"아무것도 만들지 않는다"*로 읽었다.

고치면서 이번엔 **원칙에 예외를 뚫었다** — "fe-harness 가 a11y 스킬을 만든다,
단 범위를 제한한다"로 적었다. 범위 제한은 지켜지는지 검증할 방법이 없고,
**예외가 하나 생기면 두 번째는 쉬워진다.**

**답은 예외가 아니라 분리였다.** 스킬을 **독립 플러그인**으로 만들면 루프는
여전히 아무것도 만들지 않고, fe-harness 는 그것을 `frontend-fundamentals` 와
똑같이 끼운다. 원칙을 그대로 두면서 칸이 채워진다.
→ **별도 저장소**로 나눴다. 처음엔 같은 저장소·별도 플러그인으로 정했는데,
그러면 위장을 막기 위해 판정 기준("단독으로 써도 말이 되는가")을 **사람이 지켜야**
한다. 저장소를 나누면 그게 **구조**가 된다 — 설정도 `findings` 도 물리적으로
닿지 않는다. 덤으로 fe-harness 의 `source: "./"` 를 안 건드려도 되니
"캐시 갈림 때문에 1번에서 미리 구조를 나누자"던 걱정이 **통째로 사라졌다.**
문제를 만든 선택지를 버리니 문제도 없어진 경우다.

**만들지 않은 플러그인을 `dependencies` 에 적어뒀다.**
`a11y-semantics` 를 의존성과 기본 조합 양쪽에 미리 넣어뒀는데, 해결되지 않는
의존성은 `dependency-unsatisfied` 로 **fe-harness 자체를 비활성화한다.** 그대로
1번을 실행했으면 플러그인이 통째로 죽었다. 설계 문서에 "앞으로 이렇게 될 것"을
적으면서 그것이 **실행 가능한 매니페스트**라는 걸 잊었다.
→ 양쪽에서 빼고, **만든 뒤에 동시에 추가**한다는 규칙을 명시했다.

**시점도 "만든다"에서 "필요하면 만든다"로 바꿨다.**
미루는 것이 세 갈래를 연다 — 지적이 없으면 안 만들고, ①이 잡을 수 있는
종류면 ESLint 설정 문제고, 진짜 반복되면 그때 `findings` 가 목차가 된다.
그 사이 마켓에 조각이 생길 수도 있다. **미루는 것이 "조각을 만들지 않는다"에
시간을 벌어준다.**

**필수/선택 기준도 이 과정에서 고쳤다.** "루프가 성립하는가"로 잡았더니
`a11y-semantics` 가 선택으로 떨어졌는데, 기본 조합이 이름을 부르는데 없으면
그 역할이 조용히 빈다. → **"기본 조합이 참조하는가"**로 바꿨다.

**a11y 런타임을 "비싸다"는 이유로 통째로 뺐다.**
비용이 루프와 안 맞는다고 판단했는데, **틀린 건 검사가 아니라 루프가 하나라는
가정**이었다. 비용이 다른 검사를 한 루프에 몰면 둘 다 못 쓴다.
→ **이중 루프**로 나눴다. 내부(commit)는 빠르고 델타, 외부(push)는 비싸고 전체.

부수적으로 여러 게 제자리를 찾았다 —
델타 검사가 놓치는 **커밋 간 중복**을 외부 루프의 전체 스캔이 잡고,
리뷰 도구들의 기본값 `main...HEAD` 가 **외부 루프에서는 그대로 맞고**,
매 커밋마다 물으면 성가시던 **승격 제안**이 푸시당 한 번으로 적절해지고,
PR 전용이라 자리가 애매하던 `code-review`(official)가 외부 루프에 들어간다.

**그리고 트리거를 옮기는 것만으로는 안 되는 게 하나 있었다** — a11y 런타임의
진짜 걸림돌은 빈도가 아니라 **"무엇을 렌더할 것인가"**다. push 가 일어난다고
서버가 뜨는 것도 아니고, `Button.tsx` 변경이 어느 화면을 거치는지 알 방법도 없다.

**Storybook 을 1순위로 뒀던 것도 틀렸다.**
"컴포넌트마다 렌더 가능한 URL 이 이미 있다"가 이유였는데, **전체에 스토리를
만들지 않는 저장소에서는 검사되지 않는 화면이 그대로 남는다.** 도구의 장점만
보고 그 도구가 저장소에 있다고 가정했다.
→ **저장소가 이미 가진 렌더 수단에 얹는다**로 바꿨다(E2E > 컴포넌트 테스트 >
Storybook > 라우트 목록). 넷 다 없으면 이 계층은 만들지 않는다 — 없다고
스토리북·E2E 를 만들라고 요구하는 것은 범위 밖이다.

**정적 계층 플러그인을 우리가 주입해서 돌릴지도 검토했다.**
`package.json` + 락파일로 `eslint-plugin-jsx-a11y` 를 플러그인 캐시에 설치하고
`--no-config-lookup --config` 로 우리 설정만 돌리는 것은 **기술적으로 된다.**
그런데 프로젝트가 의도적으로 끈 룰을 되살리고, 파서·tsconfig 재현 실패가 파싱
에러를 코드 문제로 보고하게 만든다 — **v1 에서 실제로 겪은 사고**다.
→ **제안이 1순위**(기존 CI 를 안 깨도록 `warn` 으로), 별도 실행은 차단 금지 ·
출처 명시 · 부분집합 조건 아래 2순위.

**조사 범위를 로컬 마켓으로 한정했던 것.**
5개 마켓만 보고 "조각은 다 있다"고 결론 냈는데, 웹 조사에서 `jscpd`·`knip`·
`hone-skills`·`drywall`·`serena` 가 나왔고 **그중 중복·죽은 코드 탐지는 설계를
바꿀 만한 것**이었다. 결정적으로 잡을 수 있는 것을 판단 영역에 두고 있었다.
→ `verify` 역할을 확장하고, 부록 A-5 로 근거를 남겼다.

**필수 의존성 기준을 고쳤다가 되돌렸다.**
"기본 조합이 참조하면 필수"로 정했더니 `commit-commands` 가 딸려 왔다. record 는
`/lap` 5단계에 형식이 명세돼 있으니 폴백이 있다고 보고 기준을 **"폴백의 품질을
우리가 보증할 수 있는가"**로 좁혔다.

**되돌렸다.** 좁힌 기준은 사람이 매번 판단해야 해서 그때그때 달라진다. 실제로
첫 사례에서 결론을 정해놓고 기준을 고치는 모양이 됐다 — v1 에서 커플링 회피를
사용자 요건보다 앞세운 것과 같은 종류의 미끄러짐이다.
→ **"기본 조합이 이름을 부르는 외부 플러그인은 전부 필수."** 두 목록을 diff 하면
검증이 끝나고, 기본값이 부르는데 없어서 역할이 조용히 비는 일이 구조적으로
불가능해진다. 대신 **기본 조합에 도구를 추가하는 것이 무거운 결정이 된다** —
그건 맞는 무게다.

**`guard-components` 를 지우면서 fixtures 까지 지웠다.**
차단 훅만 폐기 대상인데 컴포넌트 탐지 fixtures 를 같이 삭제했다. 그 fixtures 는
남아 있는 `warn-components` 와 탐지 함수 테스트가 쓰고 있었다.
→ `git checkout` 으로 복구. **폐기와 그것이 쓰던 자산의 폐기는 별개다.**

**그리고 차단을 지우면 신호에 구멍이 난다.**
`warn-components` 는 "Write 는 guard 가 이미 반려했으므로 건너뛴다"고 돼 있었다.
차단을 없앤 순간 **Write 경로의 컴포넌트 신호가 통째로 사라진다.**
→ `warn-components` 가 Write 도 받도록 고치고 테스트를 추가했다.
차단을 걷어낼 때는 그 차단을 전제하던 코드를 같이 봐야 한다.

**스키마를 묶으면서 구 스키마 폴백을 넣었다가 뺐다.**
`format`/`lint` → `verify.*`, `max*Lines` → `signals.*` 로 묶었는데, 기존
`.fe-harness.json` 이 조용히 무시될 뻔해 모든 getter 에 구 경로 폴백을 달았다.
그런데 0.1.x 는 폐기하는 버전이고, **폴백은 영구히 따라다니는 이중 경로**다.

→ 폴백을 지우고 대신 `fh_legacy_keys` 로 **감지해서 알린다.** 지켜야 할 것은
"옛 키가 동작하는 것"이 아니라 **"무시된다는 사실을 사용자가 아는 것"**이었다.
읽지 않을 거면 읽지 않는다고 말하면 되고, 그건 한 번 옮기고 끝난다.

폴백을 지우자 **테스트 10개가 깨졌다** — 테스트가 전부 구 스키마 설정을 쓰고
있었다. 폴백이 있는 동안은 새 스키마를 하나도 검증하지 못하고 있었던 셈이다.
호환 계층은 회귀를 막는 대신 **검증도 같이 막는다.**

**분량 게이트를 원칙보다 먼저 옹호했다.**
1장 분류표는 파일 길이와 컴포넌트 개수를 같은 칸("셀 수 있으나 판단 필요")에
넣어 놓고, 정작 분량만 차단으로 남겨 뒀다. 근거로 든 것은 *"쓰기 전에 막을 수
있는 유일한 결정적 신호"* 였는데 **이건 분류가 맞다는 얘기가 아니라 타이밍이
편하다는 얘기**다. v1 이 무너진 지점이 정확히 거기다.

자체 기준에도 걸렸다 — *"정당하게 어겨야 하는 경우가 주 1회 이상이면 경고로
간다."* 실측 4.5% 인데 하루 10~20개 파일을 만들면 주 3~6회다. 그리고 데이터
테이블 · 타입 정의 · SVG 처럼 정당하게 긴 파일이 실재한다.

결정적으로, **이 게이트를 정당화하던 명제("새 파일은 싸게, 기존 파일은 비싸게")는
v2 가 이미 폐기했다.** 근거가 철회된 장치를 "작동하니까" 남기는 것이 잡동사니가
쌓이는 방식이다.
→ `warn-size` 로 강등. **`PreToolUse` 훅이 하나도 남지 않았다** — v1 의 중심
명제였던 "쓰기 직전 반려가 핵심"이 완전히 반대로 뒤집힌 지점이다.

**그리고 차단을 없앤 자리는 루프가 채운다.** 신호가 `findings` 로 흐르면 같은
지적이 3회 쌓일 때 루프가 규칙 승격을 제안하고, 승격 수단 중 하나가 `hookify`
차단 규칙이다. **차단할지 말지를 우리가 짐작하지 않고 사용자의 데이터가 정한다** —
이 도구가 존재하는 이유인데 정작 자기 게이트에는 그 원리를 안 쓰고 있었다.

**주입 문구가 임계값을 하드코딩하고 있었다.**
강등하며 문구를 고치다 컴포넌트 개수를 `1개` 로 박아 넣었다. 설정을 2로 바꿔도
"1개"라고 말한다. **설정을 반영하지 않는 안내는 안내가 아니라 오답이다.**
테스트도 "컴포넌트를 언급하지 않는다"는 낡은 단언이라 이걸 못 잡았다.
→ 설정을 읽게 고치고, 테스트를 **"차단한다고 주장하지 않는다"**는 진짜 불변식으로
바꿨다. 단언은 구현이 아니라 지켜야 할 성질을 적어야 한다.

**`/lap` 이 커밋을 품고 있었다.**
`DESIGN.md` 는 처음부터 "커밋은 이미 끝났다"(커밋 후)로 쓰여 있고 `README` 도
그런데, `lap.md` 만 `범위확인 → verify → review → refine → **커밋** → learn` 이었다.
`/ship` 의 배포 파이프라인 뼈대를 이름만 바꿔 물려받은 탓이다.

이건 문서 불일치로 끝나지 않는다 — **6번 훅을 붙이면 루프가 두 번 돈다.**
`/lap` 이 커밋하고, 그 커밋을 훅이 감지해 루프를 또 깨운다. 델타 기준도
`/lap` 은 `HEAD`, 훅은 `HEAD~1` 로 갈린다.

**커밋 후가 맞다.** v2 자동화의 전부인 `asyncRewake` 가 `PostToolUse` 라
본질적으로 커밋 후이고, 커밋 전으로 가려면 `PreToolUse(git commit)` 에서 막아야
하는데 그게 v1 에서 폐기한 게이트 방식이다.
→ 내부 루프를 **4단계**(verify · review · refine · learn)로 줄이고 커밋·푸시·PR 을
루프 밖으로 뺐다. 기준 ref 는 `git diff --quiet HEAD` 로 판정해 **미커밋 변경이
있으면 `HEAD`, 없으면 `HEAD~1`** 을 쓴다 — 어느 시점에 불러도 "아직 리뷰 안 된
가장 최근 변경"을 본다.

**`refine` 기본값이 계약과 어긋나 있었다.**
`refine` 은 "제안까지"인데 기본값으로 넣은 `simplify` 는 **묻지 않고 고친다.**
루프가 커밋 후로 확정되니 그건 amend 나 후속 커밋을 부른다.
→ 기본값을 비웠다. 도구 없이 모델이 직접 수정 코드까지 낸다.

그 과정에서 **역할 문법의 빈틈**도 드러났다. `""` 가 "그 역할 끄기"였는데,
정작 흔한 상태는 **"도구는 안 정했지만 단계는 돈다"**이고 그걸 쓸 값이 없었다.
`disable` 이 이미 끄기를 맡고 있으므로 `""` 를 그쪽으로 넘겼다.

**`simplify` 는 사실 refine 이 아니라 review 후보였다.**
자체 검토 축(재사용·단순화·효율·추상화 수준)을 갖는데, 다만 **고치기까지 해서
리뷰가 부수효과를 갖게 되고** 단순화·추상화 축이 `frontend-fundamentals` 의
가독성·응집도와 겹친다. 다관점 리뷰를 붙인다면 **읽기만 하고 축이 다른 것**
(`silent-failure-hunter`, `type-design-analyzer`)을 **외부 루프에** 붙이는 게 맞다.
기본값은 단독으로 두고, 두 번째 렌즈가 새 지적을 내는지는 `findings` 로 판정한다.
